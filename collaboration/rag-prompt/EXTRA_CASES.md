# 追加の合成ケース（追加練習問題）の設計案

状態: 設計案。ケース本体とコード変更は未作成。有料API0回。

## なぜ足すか

固定6ケースだけで候補指示を調整すると、そのケースへの合わせ込みになる。trial-02/03（`results/`）でも、v2・v3の指示は固定6ケースの結果を見て作っており、日付（v01-rule）と判定基準（v01-basis）の両取りが安定しなかった。explainスタイルで補足が一切出ないため、補足説明の評価もできていない。別の題材で同じ傾向が出るかを確かめる。

追加分は「追加練習問題」と呼ぶ。未使用20問ではなく、未使用20問は読まない・調整に使わない（`docs/RAG_COLLABORATION.md`）。

## 今の仕組み

- 1ケースは、質問・検索結果の抜粋・生成設定を1組にした `production-contexts.json` の要素（`key`, `status`, `baseInstructions`, `body`, `citations`）。検索結果は `baseInstructions` の末尾のJSONに入る。
- 全体は `manifest.json` の `contextsHash` で凍結されていて、書き換えると検査が通らない。
- `workspace.ts`・`run-luna.mjs`・`score.mjs`・`rubric-fixed6.json` は、この6ケースを前提にしている。

## 案

凍結ファイルは変更せず、追加分を別ディレクトリに置く。

```
collaboration/rag-prompt/extra-cases/
  contexts-extra.json   固定6と同じ形式。keyは `extra:<名前>`
  manifest-extra.json   contextsHash、作成日、作成者、レビュー者
  rubric-extra.json     原子的な採点項目。生成側へ渡さない
```

### 作る順番（守る）

1. ケースの型を決める（下表）。候補の指示や過去の回答は見ない。
2. ケース作成者が、質問・架空の資料・採点項目を書く。候補指示の作成者とは別の人にする。
3. 別の人かAIがレビューする（質問に資料だけで答えられるか、採点項目が原子的か、答えが採点項目に透けていないか）。
4. `contextsHash` を固定する。
5. そのあとで候補を評価する。回答を見てケースや採点表を直すときは、新しい版にして、前の結果を残す。

### ケースの型（題材は固定6の点灯時間・講習・バス以外にする）

| 型 | 見たいこと |
|---|---|
| 適用条件で答えが変わる（期間・版・対象） | 適用条件と、判定の基準の両方を書くか |
| 片方の値が資料にない比較 | 書けない理由を述べ、勝手に補わないか |
| 測定条件が違う値の比較 | 比較できない結論を先に書き、共通点（同じ値）は述べるか |
| 指標の意味 | 値・単位・何を表すか・何を表さないか |
| 複数の数値条件（以上・以下・範囲） | 条件ごとの値を取り違えないか |
| 別ページの2主題の比較 | 2つの出典を混ぜずに両方答えるか |
| 資料に答えがない（`status`が答えなし） | 答えがないと言い、推測しないか |
| 資料にない一般概念が質問に含まれる（explain向け） | 補足を資料と区別して示し、資料より後に置くか |

型ごとに1〜2ケース、合計8〜12ケース。今の計画なら 12ケース×2スタイル×(baseline＋候補)×3回 = 144回で、費用の概算は約0.08ドル（trial-03の72回が約0.039ドル）。

## 必要なコード変更（別PR）

評価ツールの変更なので、`docs/RAG_COLLABORATION.md` の決まりどおり、統合担当（kohtaroh928）と対象ファイルを先に合意する。

- `workspace.ts`: 読み込むケース集合を選べるようにする（既定は固定6。引数で `extra`）。
- `score.mjs`: 採点表を選べるようにする（既定は `rubric-fixed6.json`）。
- `run-luna.mjs`: 上と同じ指定を受ける。
- 固定6の既定の挙動と `contextsHash` は変えず、テストで固定する。

## 決めること

- ケース作成者とレビュー担当（候補作成者と分ける）。
- 上のコード変更をこのPRに含めるか、別PRにするか。
- 型とケース数。

## やらないこと

未使用20問を読む・使う。実資料や個人情報を使う。本番promptを変える。結果を一般的な正答率と呼ぶ。
