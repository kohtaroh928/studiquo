# RAGのページOCR補完・数式確認の改善

2026-10-09、⑤のうち、文字層が非空のPDFでも画像側の文字を確認する処理、保守的な本文補完、数式・認識不確実ページの案内を実装した。
**数式の正確な自動復元は未解決。今回の変更を数式OCRの完成とは扱わない。**

## 変更した動作

以前はPDFImportServiceのpage.stringが空の場合だけ背景画像をVisionで認識していた。本文が取れていても、画像にだけ存在する図中文字・数式が欠けるページを確認できなかった。
新しいRAGDocumentTextExtractionServiceを使い、利用者が資料登録を明示的に実行したとき、背景画像をページ単位で端末OCRする。

- 元の文字層を保持し、OCRで置換しない。出力本文にNFKCを適用せず、上付き・下付き文字を勝手に変換しない。
- 文字層があるページへの追加はconfidence 0.9以上、近似重複ではない本文候補に限定する。数値・変数・大文字略語だけの図ラベルを説明文として追加しない。
- 文字層がないスキャンは従来の日本語Vision設定を維持する。低信頼の通常本文をすべて捨てると検索が悪化するため、本文として残し、確認対象として案内する。
- 数式と判定したOCR行は補正式として追加しない。元の文字層にある数式はそのまま保持する。文脈から式を生成・修正しない。
- 低信頼・近似誤読・数式・未抽出・画像不正等をneedsReviewとしてまとめ、登録完了時に確認対象ページ数と原本確認の案内を表示する。
- 全ページを同時OCRせず、逐次処理する。iOS画像は最大辺2400pxに縮小し、5ページuploadを維持する。

数式検出は記号や短い変数のヒューリスティックであり、すべての誤式や誤読を見つけるものではない。confidenceも正確性の確率ではない。
日本語の短いラベルや一部の英語略語は保守的に除外される。表のセル・図の関係・2次元の数式構造を復元する機能ではない。

## 検証結果

| 評価 | 結果 |
|---|---|
| 合成100ページのOCR確認 | 100ページ、約19.9秒（Mac） |
| 同資料のスキャン部分 | 20ページ、固定根拠20/20を保持 |
| 同資料の実AI検索60問 | 根拠取得55/55、根拠なし5/5の出典抑制 |
| 公開教科書348ページ | 元の文字層を全ページ保持、31ページに本文補完、約108.8秒（Mac） |
| 同教科書の固定30問 | 根拠取得24/24、根拠なし6/6の出典抑制、partialなし |
| 数式の目視サンプル | 物理p40の5式を線形式に転記した基準との一致は前後とも0/5、要確認フラグあり |

数式の0/5は文字列・構造表現の確認であり、数学的同値を判定した精度ではない。分数や添字を含む式を正確に復元できたとは確認できなかった。
公開教材は既存の気象庁教科書。私有資料を無断で送信していない。スキャン20ページは生成した画像PDFであり、汚れ・傾き・低解像度の実紙スキャンの代表評価ではない。
100ページの最終本文は、60問実測に使った抽出本文と全ページ完全一致した。元の質問・正解・anchorを変更していない。

公開教科書の348/348ページに確認フラグが立った。数式・保守的な候補除外を含む確認案内であり、348ページすべてが誤読・検索失敗という意味ではない。この警告の頻度と分かりやすさは今後の調整対象。
合成100ページでは26ページが確認対象。警告の件数を検索精度と混同しない。

実Workers AIのbge-m3/bge-reranker-baseと本番indexSource/retrieveを利用した。D1相当はローカルSQLite FTS5、Vectorize相当は厳密cosineである。実D1/Vectorizeの近似検索、実iPadのOCR精度・速度、Gemini最終回答は測っていない。
MacのPDF描画は従来の1224×1584設定を維持した。iOSの背景画像・OS・認識エンジンは異なるので、このOCR速度・精度を実機にそのまま当てはめない。

## 検証中に修正した退行

補完にもスキャンにも一律confidence 0.9を要求すると、既存のスキャン本文を落としたため分岐を分けた。描画解像度の変更でも認識が変わったため、従来設定を維持した。
図の日時・単位・英語略語を補完すると、公開教材jma-08で正解ページが最終Top5から押し出され、24/24から23/24へ退行した。モデルの再順位付けスコア自体は同じだったが、RRFとの融合順位が変化した。
独立担当が代替contextを確認し、正解基準を変更せず、自然な本文と図のラベル列を区別する条件を追加した。最終再評価で24/24を回復。検索閾値やRRFの重みは変更していない。
失敗した試作の結果も集計JSONに残し、採用版と区別する。認証更新前に質問0件で失敗した試行は品質合格に数えない。

## テスト・安全確認

- 新規OCR・本文統合・状態変更テスト10件。原文保持、重複除去、数式非推測、英語見出し保持、低信頼の補完除外、100ページ/20batch/ページ境界、同意・lock・暗号化・account切替・cancelを検証。
- 最終対象テスト26/26成功。最終iOS全ユニット1,581件、Worker全749件、出典タップUI3件を検証（最終ログを別途保存）。全UI suite・実機・多分野の実スキャンは未実施。
- 独立PlannerとCode Reviewerで原因・条件・結果を確認。指摘された数式判定漏れ、空認識の案内漏れ、英語見出しの除外、状態変更後の確認を修正した。
- OCR待機前後と送信前後で同意、lock、暗号化、削除状態、canonical accountの切替を確認。別accountの削除queueへ元資料IDを入れない。
- OCR結果をrecognizedTextへ書き戻さず、編集可能ノートの消したinkを古いOCRキャッシュから復活させない。
- 本文・画像・OCR候補・prompt・Embedding・認証値をログへ追加しない。品質案内を本文へ混ぜず、sourceHashは最終本文から計算する。同じ本文の再登録では追加Embeddingなし。
- XcodeGenで新規ファイルを登録し、既知の制約で消えるApple Sign In/iCloudのSystemCapabilitiesを復元。entitlementsと生成projectの構文を確認した。

OCRは端末Visionで、新しい有料OCR API・画像送信先は追加していない。端末の処理時間・電池消費、補完本文のEmbedding量は増える。

migration、binding、secret、永続モデル変更なし。プライバシー上の送信先・保存先の追加なし。すでに同意対象の文字認識本文として補完文を送る。画像は送らない。

ロールバックは新サービス呼び出しを旧空文字OCR経路へ戻す。以前の索引が自動復元されるわけではないので、必要な資料のみ旧方針で明示的に再登録する。

## 再現と残る作業

本文を含む入力と実測原本は0700の`/private/tmp/studiquo-rag-ocr-v1`に保存。抽出JSONはexclusive新規作成・0600。既存出力の保護を実行確認した。
新しいNode driverはアプリと同じSwiftサービスを一緒にコンパイルし、同じ統合ロジックを使う。元の公開教材評価の結果は過去の空ページOCR方針で測ったものなので、現在の抽出で過去hashが再生成されるとは限らない。
結果JSONは数値・状態・ページ・hashのみ。教材本文・質問・anchor・画像・認証情報をGitへ追加していない。

本番有効化前に、数式専用の認識手段の比較、数式/不確実ページの品質情報をWorker・Geminiへ伝える設計、実紙スキャン・実iPad・多言語評価、警告の過剰表示の調整が必要。
数式認識を外部画像AIへ拡張する場合は、画像送信の同意・費用・秘密管理・誤式の評価を別途設計する。今回の本文OCR改善だけで数式教材を本番品質と判断しない。
