# RAG 回答後の根拠検証と閾値較正の設計メモ

2026-10-20。設計だけで、実装も評価の実行もしていない（実APIの費用が出るため、実施は別途決める）。OWASP LLM09（誤情報）の残件。

## 1. 現状

- 根拠の有無は**生成前**に決める（`relevance.js`・`answerability.js`・`evidence-selection.js`）。生成後に、回答が抜粋に支えられているかは見ていない。
- 関連判定の閾値（`limits.js`の`RELEVANCE`）は経験的な値で、独立した日本語・OCR・否定の評価セットで較正されていない（契約§8）。

## 2. 生成後の検証（案）

| 段階 | 内容 | 費用 | 挙動の変化 |
| --- | --- | --- | --- |
| A. 規則による検査（API不要） | 回答の数値・単位・固有名詞・型番が、抜粋に現れるかを照合し、現れないものを数える。数えるだけで回答は変えない | なし | なし（ログのみ） |
| B. 影モード | Aの結果を`status`別に集計し、誤検出率を実測する | なし | なし |
| C. LLMによる検証 | 回答の各主張が抜粋に支えられているかを、別の呼び出しで判定する | 1回答につき追加のAPI呼び出し | 不支持の主張があれば注意を付ける等 |

提案は **A→B まで先に実装**（費用なし、挙動なし）し、Bの実測を見てCに進むか決めること。Cはストリーム済みの回答には後付けできず、「回答を出し終えた後に注意を足す」か「全文を保留してから出す」かの設計判断が要る（後者は体感の遅延が出る）。

## 3. 閾値の較正（案）

- 較正に使う評価セットは、**調整に使わない保留分を分けて作る**（既存の未使用20問・goldは見て調整しない）。
- 日本語・OCRの崩れ・否定・数式・表を含め、「答えられる」「答えられない」を人が付けたラベルで持つ。
- 評価は検索だけ（生成なし）で足りる。リランクは`@cf/baai/bge-reranker-base`のため、生成のAPI費用は出ない（Workers AIの使用量は出る）。
- 指標は、答えられる質問の見逃し率と、答えられない質問の誤採用率の2つ。閾値を動かすたびに両方を見る。

## 4. 決めること

1. A→Bを先に実装してよいか（挙動を変えない）。
2. Cの実API評価を回すか、回すなら予算。
3. 較正用の評価セットを誰が作るか（人手のラベルが要る）。
