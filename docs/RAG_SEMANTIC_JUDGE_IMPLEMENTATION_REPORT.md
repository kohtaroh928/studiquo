# 意味の判定の実装：答えの有無を確率で判定する（既定は無効）

2026-10-22。[設計](RAG_SEMANTIC_JUDGE_DESIGN.md)に沿って、意味の判定を実装した。**`RAG_JUDGE` の既定は `off`** で、配備しても挙動は変わらない。集計は[RAG_SEMANTIC_JUDGE_IMPLEMENTATION_RESULTS.json](RAG_SEMANTIC_JUDGE_IMPLEMENTATION_RESULTS.json)。対象は `claude/rag-ts`。

## 経緯

設計の整理のあと、最終回答の測定で、回答のAIは答えなし9問を「資料にない」と正しく答えるが、無関係な出典が全問で表示されることが分かった（[RAG_FINAL_ANSWER_PROBE_REPORT.md](RAG_FINAL_ANSWER_PROBE_REPORT.md)）。そのため「実装は急がない」と整理したが、指示により実装した。判定の価値は、**無関係な出典の表示と、不要な抜粋の送信を抑えること**。既定を `off` にしたのは、設計で未了の確認（下記）が残るため。

## 実装したもの

| 場所 | 内容 |
|---|---|
| `src/rag/judge.ts`（新規） | Cloudflareの判定専用モデル `clef-flash` に、質問と最終の抜粋（各3,000文字、合計9,000文字まで）を渡し、「求められた情報が書かれている確率」を得る。時間の上限2秒。失敗・時間切れ・不正な応答・束縛なしは、出典を残す（fail-open） |
| `src/rag/limits.ts` | `JUDGE`（モデル、呼び出し数、時間、文字数、しきい値）。`LIMITS`・`MODELS`とは別にして、既存の契約のテストに触れない |
| `src/rag/retrieval.ts` | 認可の確認と比較の評価の後、結果を組み立てる直前で判定を呼ぶ。`on` で、1つの主題の質問は確率0.25未満で出典を外す（`insufficient`、`detail: judged_unanswerable`）、0.5未満で `partial`。比較・2主題の質問は `partial` まで。`aiCalls` に数える |
| `src/rag/contract.ts` | `EMPTY_DETAILS` に `judged_unanswerable` |
| `src/ai.ts` | `rag_retrieval` のログに `judge`（`mode`・`outcome`・`bucket`・`action`）。質問・抜粋の文字は出さない |
| `wrangler.jsonc` | `RAG_JUDGE: "off"`（既定・ステージングとも）。`off`／`shadow`／`on` |
| `scripts/rag-quality/real-material-evaluate.ts` | 評価の道具が判定を呼べるように（`STUDIQUO_RAG_JUDGE_MODE`）、結果に判定の確率を記録 |
| 文書 | `RAG_PROMPT_CONTRACT.md` の4.1、`RUNBOOK.md` のRB-21 |

`shadow` は、判定を呼んで結果をログに出すだけで、結果を変えない。まず `shadow` で割合を見てから `on` にする。

## 検証

- **Workerテスト：** 2403件中2402件成功、失敗0、スキップ1。新規13件（`src/rag-judge.test.ts`）：設定の固定、`off`が既定（`wrangler.jsonc`の全環境）、送信内容は質問と抜粋だけ、確率の検証、しきい値（比較は止めない）、時間切れ・失敗・束縛なしで出典を残す、`off`は呼ばない、`shadow`は結果を変えない、`on`の段階式、`aiCalls`、ログに文字が入らない。接続を壊すとテストが失敗することを確認した。
- **実APIの確認（Workers AI）：** 調整済みの質問（第2〜第6回、73問が判定の対象）で確認した。

| 確認 | 結果 |
|---|---|
| `shadow`：結果の変化 | **0問**（基準＝判定なしの直前の実行と比較）。判定は73回すべて成功（エラー・時間切れ0） |
| 確率：今誤って通っている答えなし9問 | 0.05〜0.24（最大は金額の質問の0.237） |
| 確率：答えあり64問 | 最小0.62。**全問「残す」** |
| `on`（第3回） | 答えなし **19/27 → 27/27**、答えあり12/12のまま |
| `on`（第5回） | 答えなし **9/10 → 10/10**、答えあり4/7のまま（残りは英字の別名の既知の問題） |

本番の経路では判定が見る抜粋が、試験（各1,500文字・3ページ）より長いので、確率は試験より高く分かれた（答えありの最小が0.29から0.62）。

## 注意点・未確認

1. **しきい値は暫定で、学習データでの値。** 上の結果は、しきい値を決めるのに使った質問での確認で、汎化の証拠ではない。金額の質問の確率は0.237で、しきい値0.25との差が小さい。有効にする前に、固定した新しい質問で、事前に決めた値を測る（設計の6）。
2. **Worker内のAI束縛からの呼び出しは未確認。** 確認はREST経由。入力の形は同じ（`{model, state, questions}`）だが、本物のWorkerでの動作は、ステージングの `shadow` で確かめる。遅延もMacからの測定。
3. **`clef-flash` の提供の安定性・版の固定・今後の価格は未確認。** 失敗はすべて出典を残すが、モデルが変わると確率の分布が変わりうる。固定した評価セットの定期的な再実行が要る。
4. **プライバシー文言とCloudflareの契約条項の確認は未了。** 新しい送信先は増えない（リランクが同じ質問と抜粋を送っている）が、確認が済むまで `on` にしない。
5. 最終回答は測っていない（出典の表示は直るが、回答の文章は変わらない）。

## 有効にする手順（案）

1. 評価の質問を新しく作って固定する（答えなし30問以上、答えあり60問以上）。しきい値を、見る前に決める。
2. ステージングで `shadow`。`rag_retrieval` の `judge` を集計し、RB-21で確認する。
3. 新しい質問で、事前に決めたしきい値の効果と、誤停止を測る。
4. 問題がなければ `on`。ログで `outcome` の失敗と `insufficient` の割合を監視する。戻すのは `RAG_JUDGE` を `off` にして再配備。
