# ホームPDF自動探索RAGと学習向け解説の設計案

日付: 2026-10-11。状態: 設計ドラフト・安全基盤のローカル実装済み。対象: `.worktrees/rag-wip`。

[Notion設計案](https://www.notion.so/3f65d67983c381dd9dd2d48c56941c4d) / [新機能タスク](https://www.notion.so/3f65d67983c381a1bfa5c43d56e05a3e)。回答品質の既存タスクと分けて管理する。

## 目的と現状

ユーザーが質問のたびにPDFを選択・登録しなくても、許可済みのホーム資料から必要なページを探し、資料に基づいた説明と理解に必要な背景説明を区別して回答する。

現在の`RAGIndexingService`は明示的な登録専用で、PDF本文の抽出・OCR補足と5ページ単位のアップロードを行う。`RAGControlsView`は資料・検索範囲の選択と送信操作を持つ。Workerにはlibrary scope、accountKeyによるVectorize事前filterとD1再照合、ハッシュ・lease・削除tombstoneがある。ホームのPDF全体を自動登録する処理と、サーバー側の自動索引用同意世代・資料の検索資格管理は今回確認した範囲では存在しない。

WorkerはiPad内のPDFを直接読めない。端末側で検索用のテキストを抽出し、許可後に自動同期する必要がある。質問ごとに全PDFをGeminiへ送信する方式は採らない。既存のAIProvider → WorkerAIProvider → Worker → Geminiを維持し、Retrievalは生成モデルから独立させる。

## 初期範囲と仮定

- 本人がホームに保存した非ロック・非暗号化・非ゴミ箱のPDFを対象とする。サブフォルダも許可範囲に含められる。
- 初回に既存PDFと将来の追加PDF、自動送信範囲・保存・削除を説明して明示同意を得る。既存の個別登録用rag-v1同意を包括同意へ読み替えない。
- 全PDF、選択フォルダ、資料ごとの除外を選べる。将来のNotebook自動同期、共有フォルダ、全端末同期は別段階。
- 初期は単一端末のホーム資料を基準にする。複数端末対応を公開する前に、資料状態の同期と失効保証の仕様を確定する。
- 「自動」の意味は手動の登録ボタンを毎回押さなくてよいこと。初回の索引作成時間や端末停止中の遅延がなくなることを意味しない。

## 1. 端末で自動索引を準備する

新規`RAGLibrarySyncService`とアカウント別の永続ローカルキューを設け、既存抽出・登録サービスを再利用する。import・PDF置換・フォルダ移動・改題・ロック・ゴミ箱・削除・除外のイベントを取り込み、起動時に資料一覧と照合して取りこぼしを回復する。

本文のテキスト層を優先し、必要なページだけ既存Vision/OCRを使う。内容ハッシュでキャッシュを管理する。5〜10ページ程度とbyte上限の両方でバッチを分け、100ページPDFを中断・再開可能にする。チャット送信時に全資料のOCRを開始しない。

PDFはsource-level hash、編集可能Notebookを追加する段階ではpage-level hashを使う。同一内容のEmbeddingを再利用する。hashは同一性を示すが更新順序を示さないため、サーバーが承認する世代・revisionと併用する。

アプリ利用中の処理を基本とし、バックグラウンド処理は補助とする。未ダウンロードPDFやアプリ終了中の資料は即座に検索可能と約束しない。待機・一部未登録・OCR確認待ち・検索可能を表示する。

## 2. 同意・資格・更新順序をサーバーで管理する

自動索引用にaccount単位のconsent epoch、安定したdocument ID、source generation、content revision、検索資格、除外状態、ジョブ・cleanup状態を追加する。migrationとAPIの詳細は実装設計時に確定し、既存migrationは変更しない。

Bearer tokenからrealSessionによるcanonical userを求め、accountKeyを生成する。各アップロードの受付・公開、検索、neighbor展開、生成モデルへの送信前に、最新の同意・資料資格・世代を確認する。クライアントのaccount IDやfolder IDを権限の証拠にしない。共有を追加する場合はサーバーACLが別途必要になる。

旧端末や待機ジョブが古いepoch/revisionで再登録することを拒否する。ユーザー指定除外は変更可能なrag source IDではなく安定document IDに結び付け、新source IDでの再登録によって解除されないようにする。同一account内での本文更新競合も比較・交換で防ぐ。

ロック・除外・ゴミ箱・同意撤回は、まずサーバーの検索資格を失効させ、その後D1/FTS/Vectorizeの物理削除を再試行する。Vectorize削除の遅延を検索許可と扱わない。失効前に既にモデルへ送信済みの本文を取り戻せるとは約束しない。

オフライン端末での変更はサーバーへ即時に伝えられない。同じ端末は失効同期待ちのRAG検索を止め、検索時に現端末の対象資料manifestと照合する。複数端末の瞬時失効は保証しない。アカウント全体を基準にする方式は、同期・失効プロトコルを設けた後に公開する。

自動索引停止、検索同意の撤回、保存データ全削除を区別する。撤回時は検索停止と旧ジョブ失効を行い、保存済みデータの扱いを説明する。アカウント削除・source削除・cleanup経路はfeature flag停止中も利用可能にする。ログに質問・タイトル・本文・Embedding元本文・生成promptを出さない。

## 3. 質問に合う資料を自動探索する

ユーザーが資料検索を有効にしたチャットでは、指定scopeがあれば守り、指定がなければ許可済みライブラリを検索する。純粋な雑談などを検索しない振り分けは将来評価対象とし、最初から強い推測で必要な検索を省略しない。

既存のVector検索Top20とD1 BM25 Top20の並列検索、RRF Top15、Reranker Top5、必要な同ページparent/neighborの展開を維持する。検索開始前にaccountKeyを必ずfilterし、本文の取得時にもaccountと最新の資料資格を照合する。資料数が増えても、全許可source IDを無制限にVectorize filterへ列挙する構成は避ける。

まずlibraryのchunk検索から命中した資料を特定する。タイトル・フォルダ・見出しによる資料候補は補助の順位信号とし、タイトル候補Top1だけに検索を固定しない。資料候補の結果と全許可範囲のchunk候補を統合し、必要な根拠や比較対象を残す。粗い候補探索を追加する場合もrecallを別計測する。

同名資料、複数版、質問対象が曖昧な場合は確認する。current page/notebook/folderを勝手にlibraryへ拡張しない。未索引資料がある場合は、全資料を調査済みと表現しない。非関連・0件・検索障害は通常AI回答へフォールバックし、資料回答と区別する。生成LLM自体の障害は別扱いであり、検索フォールバックだけでは解消しない。

## 4. 資料準拠と理解のための補足を分ける

検索の仕組みと回答の目的を分離する。資料の記載確認・引用・要約では資料に忠実に回答する。初心者向け解説では必要な基本用語・背景・考え方・具体例を一般知識から補えるが、資料の事実、一般的な補足、仮定の例を読者が区別できるようにする。未記載の製品仕様・料金・抵抗値・読めない指数を補ってはいけない。

回答styleは検証可能なenumなどで管理し、旧アプリが指定しない場合は既存方針を維持する。新しい解説モードを追加しても、自由なクライアントpromptでサーバーの根拠制約を置換させない。曖昧な質問目的は小さい確認または明示設定で扱う。

出典sourceId/title/pageNumber/chunkIdはretrieval結果から構造化して返す。背景補足を資料出典で裏付けたように表示しない。将来、回答部分と出典の対応を追加する場合も出典IDはサーバーが許可した集合へ検証し、意味上の裏付けは別評価する。引用タップは元PDFの該当ページを開く。

正確な一般知識の補足も誤り得る。資料と知識が食い違った場合は黙って置き換えず、根拠と不確実性を示す。最新制度など裏付けが必要な内容を、資料や検証根拠がないまま現在の事実として断定しない。

## 5. 費用・性能・障害

全ライブラリの初回索引は、個別登録より対象ページが増えるため抽出/OCR・Embedding・保存が増える。質問ごとに全PDFを再Embeddingしない。差分・OCRキャッシュ・上限・キャンセル・利用者別の予算で制御する。質問ごとの費用は検索量・候補数・rerankと生成contextで別計測する。具体的な金額は実際のページ数・質問数・料金で算定し、定額と断言しない。

初期は既存のバッチAPIを小さく拡張し、永続端末キューで処理する。サーバーの長時間処理や再試行が必要になればQueues等を追加する。queueメッセージは参照ID・世代等の必要最小限とし、本文の受け渡しには所有者管理・保持期限付きの保管先を設計する。重複配信や順序逆転でも冪等性と世代検査を維持する。

## 受け入れ条件・テスト

既存回答弱点W01〜W58に加え、W59〜W66で背景説明不足、条件、目的、根拠境界、難易度、具体例、学習過程の保持、資料の疑わしい記述を評価する。S01〜S10で自動探索・索引・失効・費用を評価する。全詳細は[Notion台帳](https://www.notion.so/3f65d67983c381b5ab44cf82d4c2d25f)を正本とする。

- 同じ資料で記載確認と初心者解説の対を作り、資料外補足の必要性と資料事実との区別を別採点する。
- 資料に存在する正解ページ、必要な根拠・条件・例外を人が事前指定する。採点情報は回答モデルへ渡さない。
- 100ページ、複数PDF、似たタイトル、末尾の例外、OCR・表・数式、実紙・実iPadを検証する。
- 同一PDFの再取り込み、中断再開、移動・改題・差し替え、古いbatch、順序逆転、重複ジョブ、削除とupsert競合を検証する。
- 他account指定、同意撤回、ロック、除外後のsource ID変更、共有対象除外、アカウント切替、検索直後の失効、物理削除失敗を検証する。
- 出典の対象・ページ・世代・タップ遷移を検証する。旧アプリ・無効flagの通常チャット互換を保つ。
- 新規問題、複数回、言い換え、資料順序、通常チャットと実APIの差、初回索引と質問の待ち時間・費用を分けて測る。

正確性、必要な情報の網羅性、出典対応、背景説明、わかりやすさ、適切な情報不足判断、簡潔さは別々に0/1/2で採点し、非該当はN/Aとする。捏造・漏えいは平均点で相殺しない。少数の既知問題での成功を全体の精度と扱わない。

## 段階導入と停止

1. server側の同意・資格・世代・失効プロトコルを先行実装し、旧APIとの互換を検証する。
2. 本人PDF・単一端末の明示同意後の自動同期とlibrary探索を実装する。
3. 回答style・評価対を再調整し、W03のv5確認と背景説明不足を少数問題・実APIで検証する。
4. 検索・回答・費用・安全性を実環境とiPadで評価してから段階公開する。
5. Notebook、共有、複数端末は別の安全レビューを経て拡張する。

自動索引・自動探索・新回答styleのflagは初期OFF。問題時は新機能を停止し、既存手動検索または通常チャットへ戻す。検索停止と物理削除は別であり、停止後も同意失効・削除・cleanupを継続する。削除済み・除外済みデータを旧版の索引へ戻して公開しない。

## 独立設計・安全レビュー

PlannerとSecurity Reviewerの読み取り専用レビューを実施した。指摘された、手動同意の包括同意への拡大禁止、サーバー同意epoch、document世代、安定IDの除外、オフライン失効の限界、folder IDとACLの区別を本案へ反映した。現行のaccountKey隔離を維持する。これは新機能の実装を検証した結果ではない。

## 根拠と未実施事項

- [Vectorize metadata filtering](https://developers.cloudflare.com/vectorize/reference/metadata-filtering/): account filterを検索前に適用。metadata indexの事前作成が必要。
- [Queues delivery guarantees](https://developers.cloudflare.com/queues/reference/delivery-guarantees/): queue採用時は重複・順序を前提に設計する。
- [Apple Background Tasks](https://developer.apple.com/documentation/backgroundtasks): 常時実行を前提にしない。

今回は関連コード調査・設計・独立レビュー・Notion評価項目更新のみ。実装、migration、テスト実行、実PDF送信、API課金呼び出し、デプロイは行っていない。以前の1,071件のテスト成功はこの新設計の検証結果ではない。

Projectの資料の更新: なし（設計ドラフトの追加のみ。構成・公開状態の変更は未実施）。方針確定・実装時にHYBRID_RAG、SECURITY_AND_PRIVACY、利用規約/プライバシー開示、同意UIの更新対象を改めて確認する。

## 安全基盤の実装追記（2026-10-11）

並べ替えた工程の1番目を実施。新migration0008と管理API、登録/検索/各モデル送信前の資格guard、世代CAS、削除journal/定期再試行を追加した。既存管理未導入accountだけ手動互換を維持する。一度managedへ切り替えたaccountは旧手動payloadへ戻さず、flag停止でも失効を維持する。安全なrollback先は新資格guardを持つWorkerに限る。

詳しいAPI・検証・独立レビューと残件は[RAG_SAFETY_FOUNDATION_REPORT](RAG_SAFETY_FOUNDATION_REPORT.md)。既存本文や実紙を外部送信する確認、remote migration、デプロイ、iPad自動送信は今回行っていない。本文を送信した後の取消、未同期の端末状態、共有ACL、Worker終了による未確定削除の運用解決は別の確認が必要。
