# 全文を揃えてから送る回答の待ち時間（実API、2026-10-20）

外から入った文字を含む回答（資料検索、添付ノート）は、完成した全文に1回だけフィルタをかけて送る（[RAG_PROMPT_CONTRACT.md](RAG_PROMPT_CONTRACT.md)）。その分、本文が出るのが遅れる。どれだけ遅れるかを、本番の`handleAI`経路・合成データ・実モデル`gpt-6-luna`で測った。再現: `mcp-server/scripts/rag-quality/latency-live.mjs`（`SAMPLES=2`、10呼び出し）。生データは`RAG_LATENCY_LIVE_RESULTS.json`（時間と文字数のみ。本文は含まない）。OpenAIの応答は、バッファせずに素通しして、最初のトークンと最後の時刻を別々に記録した。

- 15秒を超えた添付ノート・長い回答では、`: keepalive`が1回送られた（アプリは無視する）。

## 体感への影響

**本文が出るまでの余分な待ち**は、「モデルの最初のトークン」と「完了」の差。
- 短い回答: **0.3〜0.7秒**。ほぼ気づかない。
- 長い回答: 資料検索で**約4〜5秒**、添付ノートで**約10秒**。流れ始めるはずだった時刻から、全文が出るまで本文が空のまま待つ。

ただし、このモデルは最初のトークンまでに**もともと2〜13秒かかる**（資料検索・ノートの長い回答で7.2〜8.8秒、通常のチャットの長い回答で10.5〜13.5秒。質問が違うので、直接は比べられない）。つまり、長い回答では、ストリームでも、本文が出始めるまで7秒以上は待っている。保留で、その待ちが合計で11〜19秒になる。

## 判断

- **短い事実の質問（資料検索の主な使い方）**: 影響はほぼない。
- **長い解説（学習アプリの`explain`や、ノートの解説）**: 11〜19秒、画面に何も出ない待ちになる。許容できないほどではないが、**はっきり遅く感じる**。ストリームなら、モデルが書き始める7〜9秒（ノート・資料検索）から本文が流れ始める。
- 計測の限界: 各2回で、変動が大きい（最初のトークンが7〜13秒）。`gpt-6-luna`だけ。空の吹き出しの見え方（アプリの待機表示）は、確認していない。
