# 質問操作候補の初版診断

2026-10-15。自動継続の小単位。評価専用の新規合成6問・16要求行と、日本語キューから操作候補を拾うprototypeを追加した。runtimeへ接続せず、v1出力を維持。追加API送信/費用0。

## 実装したもの

- `question-task-fixture.mjs`: 料金、配送、計算、条件例外、学習解説、矛盾要約の6問。要求ごとにID/操作タグ/属性/原質問のspanを付けた手書き内訳。既存50問bankと別の開発用で、未使用20問やblind評価の代わりではない。人間確認pending。
- `question-task-probe.mjs`: 質問文字列だけからlookup/compare/recommend/calculate/explain/conditions/summarizeの候補と原文spanを返す。複数候補を許可し、根拠支持はunknown、対象/属性の対応はpending。goldや資料本文を引数に取らない。数字の答え・比較許可を生成しない。
- 既知の否定/引用/メタ命令/曖昧指示語・未知書式はneeds_review。正当な「比較して」「計算して」は依頼として扱う。有限の表層キューであり、未知の否定や固有名を理解できるわけではない。
- 初版の結果を [RAG_QUESTION_TASK_RESULTS.json](RAG_QUESTION_TASK_RESULTS.json)、code/fixture/result hashと追加対照を [初版manifest](RAG_QUESTION_TASK_INITIAL_MANIFEST.json) へ保存。結果を見て6問へ合わせる修正はしない。

## 結果と独立レビュー

料金・配送・計算・矛盾要約では手書き操作タグの集合と一致。条件例外・学習解説ではlookupタグが一致しなかった。全6問で原子的要求の網羅性・対象/属性・根拠支持は未判定のまま。これは4/6の質問正解率ではない。

独立レビューで**操作区分の曖昧さ**が判明した。「密度の式と記号の意味を説明」は、式を別lookupとせずexplainの対象に含める読み方もある。「送料込みの最終支払額はいくら」もcalculate/deriveの依頼と読め、手書き内訳のlookupだけが正解とは限らない。したがってmissing lookup2件は、現時点では**手書き区分との不一致**であり、理解能力の確定的な欠落とは呼ばない。人間gold確認と区分の明文化が残る。初版タグを正解へすり替えたり、元のgoldを無言で修正しない。

追加対照では「比較ライトAの価格はいくら」からcompareを余計に拾った。独立レビューでも「要約機能は使えるか」からsummarizeを誤検出することを確認。引用で囲まれない製品語を区別できない。現4テストはこの誤検出を防止した証明ではない。表層キューだけでは本番の要求分解に不足するため、prototypeは評価専用に留める。

## 次版前に固定する規約

1. 質問の発話操作（説明/計算/比較など）と、回答に含める属性（式/単位/価格など）を別にする。同じ操作で2属性を求めることと、2種類の操作を求めることを混同しない。
2. 「値はいくら」という情報要求と、その値を取得するか導出するかを別にする。質問/履歴だけで方法が決まらないときは曖昧と記録し、資料支持の確認へ回す。
3. 明示の比較と推薦に暗黙に必要な比較を分け、oracleの適用条件を先に定義する。操作の一致だけで子項目の網羅を認定しない。
4. 許容する複数ラベルと未確定ラベルをoracleに持たせ、独立確認してから次の候補と比較する。初版のhash/結果は保持する。
5. 固有名中の操作語・否定条件の質問・メタ命令と正当な依頼の反例を追加し、未対応を可視化する。本番のID/固有名分岐で解決しない。

今回は次版を実装せず、次回の再開位置を区分規約の明文化へ更新する。利用量制限を回避せず、次のheartbeatで最新状態から続ける。
