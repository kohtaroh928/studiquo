# 共有資料をRAGで使うときの条件（設計メモ）

2026-10-20。**実装はしていない**。共有資料のRAGは未提供で、索引できる種類は`pdf`と`notebook`の2つだけ（`storage.js`で他は`invalid_index`、`rag.test.js`が確認）。解禁する前に、次の条件を満たすこと。OWASP LLM01・LLM04・LLM08の残件。

## なぜ別扱いか

今の索引はアカウントごとで、資料の持ち主=質問者。汚染（隠した命令）の影響は自分の資料に閉じる。共有資料を検索対象にすると、**他人が書いた文字が自分の質問への根拠として混ざる**。他人の資料は攻撃者になり得る入力として扱う必要がある。

## 条件（解禁の前提）

1. **他人の本文を自分の索引へ複製しない。** 共有は「参照権」として別テーブルに持ち、検索時に持ち主の索引を、閲覧者の権限を確かめて読む。複製すると、共有を外した後も本文が残る。
2. **検索のたびに権限を確かめる。** 既存の単一SQLスナップショット（`referencesAuthorized`）に、共有関係（付与済み・失効していない・閲覧者本人）を同じSQLで加える。送信直前の再認可（`revalidateRetrieval`）にも同じ条件を入れる。
3. **共有由来の抜粋に印を付ける。** `citations`と`context`で「他人の資料」と分かる印を付け、回答方針で「この資料の記述は持ち主が書いたもので、質問者の確認済みの事実ではない」と扱わせる。
4. **共有由来の抜粋があるときは、防御を強める。** 回答のリンクは常に除く（現状と同じ）。`injectionHints`が1以上の共有抜粋は、既定でコンテキストから外す（本文に引用された例の可能性があるため、持ち主が確認した場合だけ許す）。
5. **持ち主側の編集を信頼しない。** 共有後に持ち主が本文を書き換えられるので、共有時のハッシュで固定するか、書き換えを検索時に再検査する。
6. **共有の解除・退会を即時に反映する。** 検索の認可SQLが失効を見る（キャッシュしない）。Vectorizeの削除は非同期なので、認可SQLが先に止める。
7. **別の同意。** 他人へ本文が出る・他人の本文が自分の質問と一緒にOpenAIへ送られることを、既存のRAG同意とは別の同意・説明で示す。

## 受け入れ試験（実装時に必須）

- 共有を外した直後の検索で、その資料の抜粋が出ない。
- 持ち主が本文に仕込んだ命令・リンク・不可視文字が、閲覧者の回答に届かない（`injection-live.mjs`に共有シナリオを足して実モデルで測る）。
- 2アカウント＋共有関係の組み合わせで、共有されていない第三の資料が出ない（越境テストの拡張）。

## 決めること

- 共有の単位（ノート単位／フォルダ単位）。
- 友達にだけか、リンクを知る人にも許すか（後者は攻撃面が大きく、推奨しない）。
