# Studiquo Release Checklist

最終更新: 2026-10-05  
用途: アプリ・Workerを公開する前後の確認と、人間による公開判断

## 1. 目的と使い方

この文書は「このバージョンを利用者へ公開してよいか」を判断する共通テンプレートである。チェック項目は必要な確認を示しており、実施済み・合格・公開済みを意味しない。

対象は初回公開、アプリ更新、Workerだけの更新、緊急修正。日常の小さな開発では[DEVELOPMENT_WORKFLOW.md](DEVELOPMENT_WORKFLOW.md)を使い、公開候補が決まった時点で本チェックを行う。

1. 本文の「2〜12」を毎回のリリース記録へコピーする。
2. 記録は`docs/releases/`配下に、例として`2026-10-05-initial-release.md`のような日付・識別名で保存する。例の日付は公開予定を指定するものではない。
3. 担当・対象・確認結果・証拠を埋め、不足を解消する。
4. 人間が公開判断と対象操作を承認した後、計画に沿って公開する。
5. 公開後の確認結果まで同じ記録へ追記する。共通テンプレート自体には毎回の合格チェックを残さない。

詳細な正本は次を参照し、設定値・保持期間・移行手順を重複管理しない。

| 文書 | 参照する内容 |
| --- | --- |
| [ARCHITECTURE.md](ARCHITECTURE.md) | 構成、責務、外部連携 |
| [SECURITY_AND_PRIVACY.md](SECURITY_AND_PRIVACY.md) | 認証・権限・個人情報・削除の基準 |
| [DATA_AND_MIGRATIONS.md](DATA_AND_MIGRATIONS.md) | スキーマ変更、移行、backup、復元、新旧互換性 |
| [PRIVACY_RELEASE_CHECKLIST.md](PRIVACY_RELEASE_CHECKLIST.md) | 現在のプライバシー変更固有の公開条件 |
| [cloudkit-verification.md](cloudkit-verification.md) | 過去のCloudKit確認記録。今回の実機確認の代用にはしない |

**この文書の作成や「チェックして」という依頼は、push、merge、ストア提出、deploy、本番migration、secret変更、本番データ削除の許可ではない。** それぞれの対象・環境・操作について明示的な承認を必要とする。

## 2. リリース対象と担当

```markdown
リリース名・目的:
種別: 初回公開／アプリ更新／Worker更新／緊急修正
予定日時・タイムゾーン:
公開する機能・変更内容:
公開しない機能・停止方法:
アプリversion・build番号・対象commit:
配布するArchive／ビルドの識別情報:
Worker対象commit・配布version:
対象環境・database・namespace:
migration番号・適用済み状態:
サポート対象の旧アプリ・OS・端末:
公開担当・確認担当・独立レビュー担当:
最終承認者・公開後監視担当:
```

小規模開発では担当の兼任は可能だが、Highリスク変更の独立レビューは実装者だけで済ませない。役割が未定なら未確認として扱う。

## 3. 確認結果の記録規則

各チェックIDについて下表の形式で記録する。チェックボックスは、証拠付きで「合格」または理由付き「対象外」と判断した後にだけ付ける。不合格を対象外に変更して処理しない。

| ID | 状態 | 担当・日時 | 対象ビルド・環境・端末 | 証拠・結果 | 残る問題・対応先 |
| --- | --- | --- | --- | --- | --- |
| 例: Q-01 | 未確認 | 未定 | 未定 | 未実施 | 確認予定を記載 |

- 状態は「未確認／合格／不合格／対象外」の4種類。
- 「対象外」は根拠と確認者を記録する。Workerのみの更新ならストア素材は対象外にできるが、旧アプリとの互換性は対象外にしない。
- 証拠にはテスト結果、実機記録、レビュー、設定確認などの参照先を使う。secret・token・利用者の本文を記録へ貼らない。
- 過去のテスト件数を今回の結果として転記しない。検証したcommitと配布候補を照合する。
- コード、設定、migration、契約・申告内容が変わった場合は、影響する項目を未確認に戻す。
- CIが未整備なら手動検証の結果を残す。「CI成功」とは記載しない。

## 4. 品質・主要操作

- [ ] Q-01: 配布候補のアプリbuild／ArchiveとWorkerのテストが成功し、警告・失敗・未実施の扱いを説明した。
- [ ] Q-02: 変更に近いテストと関連する回帰テストを実行した。変更していない主要操作も最低限確認した。
- [ ] Q-03: 対象iPad・OSで、新規インストールとサポート対象旧版からの更新を確認した。
- [ ] Q-04: 起動、ノート作成・編集・保存・再起動後の表示が成立する。
- [ ] Q-05: 資料取り込み・書き出し・backup復元・ゴミ箱・保護ノートを、公開範囲に応じて確認した。
- [ ] Q-06: 回転、画面サイズ、Split View、文字サイズ、主要なアクセシビリティと対応言語を確認した。
- [ ] Q-07: 通信なし・通信失敗・権限拒否・空状態・容量不足で、データ喪失や操作不能にならないことを確認した。
- [ ] Q-08: 起動時間・大きいライブラリ・描画・メモリなどの対象性能を確認し、今回の許容値と結果を記録した。

性能の合格値は対象変更と端末に合わせて事前に決める。計測していない項目に合格値を後付けしない。

## 5. セキュリティ・プライバシー

- [ ] S-01: 公開する認証方式でログイン・ログアウト・期限切れ・失効を確認した。
- [ ] S-02: 別アカウント・別ルーム・別文書・未認証者からのアクセス拒否を確認した。
- [ ] S-03: 退会の削除範囲、サーバー受理、外部削除待ち、端末削除失敗後の再試行、再登録方針を確認した。
- [ ] S-04: AI許可・拒否・取消し、送信内容・送信先、翌日復習などの自動処理が説明と一致する。
- [ ] S-05: 診断・問題報告の初期設定、画像の閲覧権限、保持・削除処理を確認した。
- [ ] S-06: 配布物・コード・設定・ログにsecretや不要な個人情報がない。外部連携は必要な権限に限定した。
- [ ] S-07: Privacy Manifest、アプリ内・Webの説明、ストア申告が、公開する実装と一致する。
- [ ] S-08: 外部サービスの契約・対象年齢・データ取扱条件について、責任者が確認した。
- [ ] S-09: 変更のリスクに応じたコード・セキュリティ独立レビューを実施し、重大な指摘を解消した。

現在のプライバシー変更には[専用の公開条件](PRIVACY_RELEASE_CHECKLIST.md)も適用する。AIを停止して公開する場合も、停止がAPI・バックグラウンド処理へ効き、利用者向け説明が一致することを確認する。

## 6. データ・新旧互換性

- [ ] D-01: スキーマ・JSON・key・relationship・削除規則の変更と影響範囲を整理した。
- [ ] D-02: 空の環境だけでなく、旧データからの移行、途中失敗、再実行、重複防止を検証した。
- [ ] D-03: backupの範囲、権限、保持期間、復元試験、許容データ損失時間・復旧時間を確認した。
- [ ] D-04: CloudKit同期ON／OFF、実機の端末間同期、新旧端末の混在を確認した。
- [ ] D-05: 「旧アプリ＋新Worker」「新アプリ＋旧Worker」で、対応範囲と失敗時の案内を確認した。
- [ ] D-06: migration適用状況、コード更新・backfill・機能有効化の順序、停止条件を記録した。
- [ ] D-07: 復元で削除済みアカウントや失効tokenを復活させない手順を確認した。

具体的な方法は[DATA_AND_MIGRATIONS.md](DATA_AND_MIGRATIONS.md)を参照する。移行ファイルの存在、ローカルでのSQL成功、CloudKit設定の存在を、本番適用・実機同期の成功と混同しない。

## 7. 本番設定・外部連携

- [ ] E-01: 開発・検証・本番のendpoint、database、KV namespace、CloudKit環境を照合した。テストが本番データを変更しない。
- [ ] E-02: 公開用設定とsecretの存在・権限・有効性を確認した。placeholderや開発用値が残っていない。
- [ ] E-03: 公開する課金商品の価格表示・Product ID・entitlement・プラン対応が一致し、購入・復元・期限切れを確認した。
- [ ] E-04: RevenueCatのidentity連携、Webhook認証・重複・遅延・失敗処理を確認した。
- [ ] E-05: 公開する通知、メール確認、チャット、共同編集、MCPの主要操作と権限を確認した。
- [ ] E-06: 管理画面・管理API・問題報告画像が、管理者認証なしでは取得できない。
- [ ] E-07: 定期処理・削除ジョブ・利用量制限の設定、実行結果、滞留監視を確認した。
- [ ] E-08: 外部サービスのquota・費用・障害時動作・通知先を確認した。

外部操作の試験は許可された検証用データ・アカウントで行う。本番顧客削除や実課金を、通常テストの代わりに実行しない。

## 8. App Store提出準備

- [ ] A-01: Bundle ID、version／build番号、署名、provisioning、entitlementsが配布候補と一致する。
- [ ] A-02: XcodeGen生成後のSign in with Apple、CloudKitなどのCapabilitiesを確認した。
- [ ] A-03: アプリ名、説明、スクリーンショット、対応言語、年齢区分、購読説明が実際の公開範囲と一致する。
- [ ] A-04: privacy policy・サポートURL・問い合わせ先が利用者と審査担当から利用できる。
- [ ] A-05: 必要な審査用アカウント・操作説明を用意し、公開範囲を審査できる。認証や安全性を迂回する審査用裏口を作らない。
- [ ] A-06: 提出時点の公式要件を確認し、必要な申告・契約・輸出関連等の回答を責任者が確定した。

最新のストア要件をこの文書だけで保証しない。審査資格情報は安全な提出先で管理し、Gitのリリース記録には載せない。

## 9. 公開判断

最終判断は「公開可／条件付き公開可／公開不可」のいずれか。AIは根拠と判断案を整理し、最終承認は人間が行う。

以下に不合格・未確認がある場合は公開不可とする。

- 重大な認証・認可・個人情報・secretの問題
- データ喪失、移行・復元の重大な未解決リスク
- 提供する重要機能である認証・保存・課金・退会の不成立
- 必須の契約・申告・利用者への説明の不足
- 本番設定、停止・復旧方法、監視担当の未確定
- Highリスク変更で必要な独立レビューの未完了

条件付き公開は、軽微な既知問題について影響・回避策・担当・期限を記録し、人間が承認した場合に限定する。上記の必須条件を例外扱いで通さない。

機能を公開対象から外す場合は、画面を隠すだけでは不十分。API、旧クライアント、自動実行からも利用できないことを確認し、説明・課金対象を合わせる。対象外の問題が共通基盤へ影響する場合は公開を止める。

```markdown
公開判断:
根拠となる確認ID・証拠:
未解決事項・影響・回避策・担当・期限:
公開から外す機能と停止確認:
承認者・承認日時:
承認した対象build・commit・環境・操作:
```

## 10. 公開実行・停止・復旧

- [ ] R-01: migration、Worker、アプリ、設定変更の実行順・担当・所要時間を決めた。
  - スライド機能の除去に伴い、Worker(`create_slides`ツールの削除)を先に公開し、アプリを後に公開する。順序を逆にすると、旧版が溜めたスライド取り込み依頼を新アプリが通知なしで破棄する(経緯: [SLIDES.md](archive/SLIDES.md))。
- [ ] R-02: 公開範囲・段階公開方法・監視期間・拡大条件を決めた。利用できない段階公開機能を前提にしない。
- [ ] R-03: 各外部操作の明示的な承認と、対象環境・versionを実行直前に照合した。
- [ ] R-04: エラー率・認証失敗・保存失敗・課金不整合・削除ジョブ滞留など、今回の停止条件と通知先を決めた。
- [ ] R-05: Worker切戻し、機能停止、アプリ修正版配布、データ復元を区別して復旧手順を用意した。
- [ ] R-06: 実際に適用したversion・migration・設定・日時・担当・結果を記録した。

アプリは公開後すぐに全端末を旧版へ戻せるとは考えない。旧版との互換性維持・機能停止・修正版を備える。コードを戻しても削除済みデータは戻らない。データ復元は別承認と削除要求の照合を必要とする。

## 11. 公開後の確認と終了

- [ ] P-01: 公開直後に安全な確認用アカウントで起動・認証・保存などの主要操作を確認した。
- [ ] P-02: migration、定期処理、Webhook、削除ジョブ、外部連携の稼働を確認した。
- [ ] P-03: 計画した監視期間中のエラー・性能・利用量・費用・問い合わせを確認した。
- [ ] P-04: 停止条件への該当を判断し、必要なら承認された復旧手順を実行した。
- [ ] P-05: 条件付き公開の残件に担当・期限があり、監視結果・障害・次の対応を記録した。
- [ ] P-06: 公開結果と監視担当の引継ぎを記録し、今回の作業を終了した。

「提出済み」「審査承認済み」「利用者へ公開済み」「公開後確認済み」は別の状態として記録する。公開前チェックだけで公開後の成功を主張しない。

## 12. チャットでの依頼例

### 初回公開前

> `docs/RELEASE_CHECKLIST.md`に沿って初回公開の準備状況を確認してください。合格・未確認・不合格・対象外を分け、証拠と公開判断案を記録してください。ストア提出・本番変更は行わないでください。

### アプリ更新前

> 今回はノート共有機能を変更しました。リリースチェックを行い、他人の資料へのアクセス拒否、旧版との互換性、保存機能の回帰を重点確認してください。公開はまだ行わないでください。

### Workerだけ更新する前

> Worker更新について該当項目を確認してください。旧アプリとの互換性、migrationの順序、失敗時の戻し方を確認し、ストア項目は対象外の理由を記録してください。本番には適用しないでください。

チェック依頼の範囲を越える外部操作や実データ変更が必要になった場合は、そこで止め、必要な対象・権限・リスクを利用者へ説明する。
