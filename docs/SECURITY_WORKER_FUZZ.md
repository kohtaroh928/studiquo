# Worker入力ファジング

2026-11-04、`origin/main` の `31599e6` を基点に、専用ブランチ `codex/worker-fuzz` で実施した。アプリのファイル解析ファジングとは別の検査である。

## 結果

2026-11-04の3シードで計194,401ケースを実行した。2026-11-05には検査ランナーの後片付けを改善し、64,804ケースを再実行した（合計259,205ケース）。5検査群すべてでプロセスグループの終了を確認した。アプリ本体での異常終了・時間切れ・署名の偽造・グローバルなprototype汚染は確認していない。一方、入力検証とエンコードの厳密性についてLowの修正候補3群がある。未修正のため `--enforce` の終了コードは1であり、「検査に合格」とは扱わない。詳細な経路・最小例・件数は非公開GitHub Projectの既存ファジング項目と修正用ドラフト、ローカルの `security-reports/` に記録する。

| 分類 | 所見 | 判定の限界 |
|---|---|---|
| JSON本文の型 | オブジェクトを文字列へ変換する一部経路で、不正型が500応答になる | 一部は未認証でも到達。全体停止・権限昇格は確認していない |
| CBOR | 一部の文字列・キーの意味が変化し、継承プロパティを利用する形も受理される | 正しい暗号署名は依然必要。Object.prototype全体の汚染ではない |
| DER署名 | 末尾データ・余分な整数・整数の非正規な表現を受理する | 既存の正しい署名の表現を変える問題。新しい内容への署名偽造ではない |

独立セキュリティレビューでも同じ3群をLowと評価した。ローカル合成鍵で、継承プロパティ内の正しい署名と、末尾データを加えた正しい署名が検証されることを担当者とは別のエージェントが再現した。改変clientDataは拒否される。本体コードの修正・公開・配備は行っていない。

## 検査内容

- CBOR: 小さな正規エンコーダーとの往復、乱数変異、末尾追加、巨大な長さ宣言、深さの上限、予約的なJavaScriptプロパティ名、先頭U+FEFF。
- DER/X.509: 正規ECDSA整数の往復、空・負・余分な整数、非最小表現、末尾追加、公開のApple trust anchorの正例と構造変異。検査用の署名は実行時に生成する。
- JSON/base64: UTF-8を分割した有限ストリーム、実バイト上限、Content-Lengthの食い違い、不正JSON、正常/不正base64。独立したJSON.parse/UTF-8復号との比較。
- token/challenge: 署名必須の合成鍵設定で正例を確認し、変異・切り詰め・別の署名ラベル・追加バイトを拒否するか検査。秘密鍵やtoken本文をレポートへ出さない。
- HTTP: 一時Miniflare/workerdの実ハンドラー・SQLite DO・KVで型変異と壊れたJSONを送信し、500と最後のlivenessを確認。外部fetchは禁止し、試行0を要求。App Attestは別のroute-level検査で、有効なローカルchallengeを伴う600個の不正attestationを確認する。

既存の認証/App Attest/OAuth等の対象テストは2026-11-04に終了コード0、Workerと専用検査コードの型検査も同日に成功。2026-11-05の最終版では生成器・CLI・停止管理の自己テスト17件と専用型検査が全成功。新規検査コードに対するGitleaksの検出は0。今回のファジングはブランチ1件目の認可マトリクスを取り込まない独立ブランチである。

GitHub Projectの既存ファジング項目に実施結果を追記し、修正候補3群をそれぞれ非公開ドラフトへ記録した。Worker側の今回の実行は終了、修正とアプリ側ファジングは残件として保持している。Projectの資料の更新: なし（テスト追加・実施記録のみ）。

## 再実行

```sh
cd mcp-server
npm ci --ignore-scripts
npm run security:fuzz:test
npm run security:fuzz:typecheck
npm run security:fuzz -- --seed 1398034773
```

`security:fuzz` は検出結果があると1、実行失敗は2、検出なしは0を返す。既知の所見を無視してCIを緑にする例外は追加していない。通常CIへの自動組込みは今回行わず、修正後に停止条件を判断する。

Node側の親プロセスが検査群を順に起動する。各群はNode heap 192MiB、45秒、標準出力1MiBの上限があり、異常時やSIGINT/SIGTERMの中断時はその検査のプロセスグループへ停止を要求する。子のcloseとグループ消滅を確認し、停止を確認できなければ実行失敗として次の群を起動しない。報告書の保存失敗も固定エラーと終了コード2で区別する。**192MiBはV8 heapだけの上限であり、RSSやworkerd子プロセスを含む全体の上限ではない**。レポートのmaxRSSも親側Nodeの観測である。

ランナーは独立コードレビューで中断処理・終了確認・保存失敗の判別を指摘され、2026-11-05に対応した。合成の子/孫プロセスと、実際のCLIへのSIGINT/SIGTERMで後片付けを検証している。対応後の独立再レビューに追加の修正指摘はなかった（コード読み取りであり、レビュー担当による自己テストの再実行ではない）。

乱数のバイト列と変異操作はシードで再現するが、暗号用の合成鍵・署名は毎回新規生成するため同一バイト列を保証しない。鍵・資格情報・利用者の資料をfixtureに保存しない。

## 残る範囲

これは有限のシード付き変異検査で、網羅的な形式検証、coverage-guided fuzzing、持続的負荷試験、任意の低速/無限ストリーム、OS全体のメモリ上限の検査ではない。実Cloudflareのedge・伝播・分散状態、実Apple attestation、iPadは対象外。runtimeは安定Miniflare対応の2026-07-30を使う。アプリ側のZIP/PDF/DOCX等は次の別作業であり、本結果で完了にしない。

根拠となる形式仕様: [RFC 8949（CBORのデータモデルと文字列）](https://www.rfc-editor.org/rfc/rfc8949.html#name-major-types)、[RFC 3279 §2.2.3（ECDSA署名のDER符号化）](https://www.rfc-editor.org/rfc/rfc3279.html#section-2.2.3)。独自実装の受理範囲と、署名そのものの成立を区別して評価する。
