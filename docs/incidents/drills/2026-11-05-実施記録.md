# 机上訓練の実施記録(2026-11-05)

## 何をしたか(この記録の限界)

これは**人が集まって声に出す訓練ではない**。Claudeが、3つのシナリオ([AIキー漏えい](drill-ai-key-leak.md)・[確認コードの悪用](drill-email-code-abuse.md)・[他人の資料の不正閲覧](drill-unauthorized-access.md))の各ステップについて、RUNBOOK・コード・設定を実際に開き、「手順が存在するか」「書かれた手段が実際に効くか」「記入欄が埋まっているか」を一つずつ確かめた**紙の上の点検**である。

| 確かめたこと | 方法 |
|---|---|
| 止める手段が実際に止めるか | `cd mcp-server && npm run security:incident-drill`(実際のWorkerを手元のMiniflareで動かす。63項目) |
| 鍵を交換すると新しい鍵で動き、旧い鍵が通らないか | `npm run security:key-rotation-drill`(34項目) |
| 戻した後に失効・退会が復活しないか | `npm run security:restore-drill`(`BACKUP_AND_RECOVERY.md`) |
| 記入欄・連絡先・権限 | RUNBOOKの表を読む |

**人の判断・連絡・所要時間の測定は含まれない。** 「誰が何分で止められるか」は、まだ測っていない。年1回の訓練の実績にはならない。責任者が参加する本番の机上訓練は、下の「人が必要なこと」を埋めてから1回行う。

## 見つかった抜けと、その対応

| # | シナリオ | 見つかったこと | 対応 |
|---|---|---|---|
| 1 | 全部 | RB-18の「操作できる人」「事前に承認済みの範囲」、RB-19の連絡先・当番・応答目標が**すべて空欄**。「止める手段」は実在するが、**誰が実行してよいかが決まっていない** | 責任者の記入が必要(GitHub Projectの項目「インシデント時の連絡先・予備の管理者・事前承認の範囲・公開窓口を決める」) |
| 2 | 全部 | RUNBOOKは`MAINTENANCE_MODE`が退会・ログアウトを止めないと書いていたが、**実装では止まる**(訓練`M3`・`M4`) | RUNBOOK RB-18を実装に合わせて修正した。メンテナンス中の退会を通すかは責任者の判断事項として記録 |
| 3 | 3(不正閲覧) | 問い合わせの窓口(`SECURITY.md`、`/.well-known/security.txt`)が**リポジトリにも配信にも無い**。利用者が不正を知らせる場所が、アプリ内の「問題を報告」(Slack通知のみ)だけ | 未対応。窓口の文面と連絡先は責任者の決定が要る(上の項目1と同じ) |
| 4 | 2(確認コード悪用) | メール送信の**全体の急増**を知らせるアラートが無い(`MONITORING.md`が「未実装」と明記)。気づく手段はResendの通知とバウンス率だけ。Resendの通知が誰に届くか、設定済みかは未確認 | 責任者がResendの通知先を確認する。アラートの実装は別項目 |
| 5 | 1(AIキー) | OpenAIの月額上限と通知の宛先が設定済みか、**コードからは確認できない**。失効の権限が責任者のアカウントだけで、不在時の代理が無い | 責任者の確認が必要(項目1) |
| 6 | 1(AIキー) | 「キーを失効する」と「`AI_PROVIDER_APPROVED="false"`でAIを止める」の違い: 後者は配備の数分かかる(`wrangler.jsonc`の`vars`→配備)。Cloudflareのダッシュボードで変数を直接変えると速いが、次の配備で上書きされる。**所要時間は未計測** | 本物のステージングでの切替訓練が必要(GitHub Projectの「キルスイッチの実地訓練」) |
| 7 | 3(不正閲覧) | 「認可の表で該当ルートを確認」とあるが、表(`app.test.ts`の`ROUTES`)は**認証の種別**の網羅で、所有者/メンバー/非メンバーの網羅ではない(ブランチ`codex/authz-matrix`が別に作成中) | 認可マトリクスのマージを待つ(別担当) |
| 8 | 3(不正閲覧) | 影響人数の見積もり: アクセスログの保持期間と、個人を特定せずに数える方法が**手順書に無い**(`invocation_logs`は無効) | 手順の追加が必要。ログの保持の仕様を責任者が決める |
| 9 | 全部 | 機能別の停止(`DISABLED_FEATURES`)は、名前の打ち間違い(`chats`)を**黙って無視する**。`/health`に載った名前で効いたかを必ず確認する、と手順に書いてあるが、シナリオ側の手順には出てこない | シナリオ3の手順3に「`/health`で確認」を足した |
| 10 | 全部 | `REQUIRE_SIGNED_TOKENS="true"`のまま`TOKEN_SIGNING_KEY`を消すと、署名の検査が**通す側に倒れる**(鍵の訓練`T14`)。鍵の失効を急ぐ場面で起こしやすい | RUNBOOK付録Aに追記した。鍵の変更後は`/health`の警告を確認する |

## 人が必要なこと(この点検では埋められない)

1. 責任者・技術担当・連絡担当・代理の氏名と連絡手段、応答目標(RB-19の表)。
2. 緊急時に確認なしで行ってよい操作の範囲(RB-18の表の最後の欄)。
3. 利用者向けの窓口(`SECURITY.md`、`security.txt`、サポートのメール)。
4. Resend・OpenAI・Anthropic・Cloudflare・Apple・GitHubの、アカウントの回復手段と通知先。
5. 通知義務(個人情報保護委員会、海外の利用者、Apple、提供元)の確認を、専門家に頼む(RB-19)。
6. 上の1〜5を埋めたあとの、**人が集まる机上訓練を1回**。所要時間と、詰まった所をここに追記する。

Projectの資料の更新: なし(運用文書と検査コードのみ)。
