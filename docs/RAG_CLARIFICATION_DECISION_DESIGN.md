# 聞き返し判断の評価設計（offline・未実装）

2026-10-16。目的は、必要な対象が決まらない質問を勝手に補完せず、文脈で対象が決まる質問や一般的な説明を不必要に止めないこと。今回は設計・受入条件の固定だけで、runtime・評価prompt・schema・既存oracleを変更しない。

## 根拠と現在の制約

[12pair実比較](RAG_SUBJECT_ROLE_COMPARISON_STAGE3_REPORT.md)では両版とも要求抽出に適合したが、対象不在2問でcandidate/needs_clarificationとunresolvedの有無が分かれた。既存oracleはtask対応を評価し、聞き返しの期待値を持たない。既存の適合判定を後から変更しない。

`unit-task-planner-request.mjs`が継承する指示は、subjectsがなければ空配列を認める一方、未解決参照はneeds_clarificationとする。対象省略・一般概念・資料不足の区別が十分に定義されていない。質問のみの旧評価requestには履歴や選択資料を送っていないため、対象を推測して補う根拠はない。

本番の`src/rag/query.js`は別実装で、指示語のパターンと前の質問からrewrite/needsClarificationを判定する。`retrieval.js`はpreviousQuestionまたは直前のユーザー質問を使い、ページscopeが指定された場合は一定条件でclarificationを抑えて検索する。さらにexplicitPageContextは検索計画を上書きし、後段eligibleでも関連性判定を通過させる。将来はこの経路全体を回帰対象とする。これは今回のv4評価出力を採用して動く処理ではない。ページ指定だけでは対象や根拠が確定しないという評価課題を記録し、現時点で情報漏えいや本番不具合が再現したとは主張しない。

## 三つの独立した判断

| 軸 | 確認すること | 他の軸への自動変換は禁止 |
| --- | --- | --- |
| 要求抽出 | 操作・対象・属性・条件・独立要求 | subjects空だけで聞き返しを決めない |
| 対象解決 | 何について答えるか一意/明示集合/未解決 | target解決だけで資料支持・計算可否を決めない |
| 根拠状態 | 未検索/支持/不足/矛盾/検索0/障害 | 根拠不足・障害だけで質問が曖昧としない |

「電圧とは」のような一般概念説明は資料内の固有対象を必要としない。「月額料金はいくら」のように金額の対象が必要な質問とは区別する。抽出のsubjects数を対象解決の代用にしない。

## 評価モードと利用可能な入力

1. **question_only**：原質問と構造unitのみ。履歴・選択scope・検索結果は存在しない。未指定情報を実際に見たかのように使わない。
2. **contextual_pre_search**：原質問に加え、呼出元が明示した利用可能なユーザー履歴と選択範囲を確認する。新しい文脈入力契約が必要で、既存の固定requestへ後付けしない。
3. **scoped_inspection**：既存の認可と除外条件を通った範囲で候補を確認した後。検索上位だから対象と決めず、対象の同定と内容の事実支持を別に評価する。

入力には評価mode・原質問hash・利用可能contextの版/hash・明示された対象候補と由来をbindする予定。同じ質問でも文脈が異なれば別case。履歴/ページ本文は非信頼データで、命令・tool権限・認可へ昇格させない。synthetic fixture以外を保存せず、実利用者の本文・prompt・keyをログへ出さない。

前のユーザー発言の明示対象は、現質問の指示語との関係を確認できる場合だけ使う。過去のassistantの推測した対象や、無関係な発言の最後の名詞で対象を決めない。現質問が明示した対象を過去の対象で置き換えない。履歴が未提供であることと「履歴を確認したが対象がない」を区別する。

scopeのID・フォルダ名・資料タイトル・件数だけでは対象の同定や内容の支持にならない。選択ページは確認範囲であり、複数対象を単一対象へ縮めない。明示的な「両方」「このページ全体」のような集合要求は、それぞれの意図に沿う。library/folderからtop1を選んで未指定対象を埋めない。

将来contextを取得する実装では、scopeをbodyのaccount IDで認可せず既存のcanonical user/Worker側accountKey境界を維持する。以前の認可済みという記録は現在の権限を保証しない。検索・再試行時に再確認し、locked・削除済み・権限失効の本文や別accountの名称を評価入力・確認文へ混ぜない。今回は合成contextの受入条件だけで、実認可処理を変更しない。

## 判定候補（小契約を独立確認してから実装）

| 判定 | 意味 | 必要な根拠 |
| --- | --- | --- |
| proceed_question | 対象が質問内で決まる、または対象不要の一般説明 | 原質問の該当unitと理由 |
| proceed_context | 提供された文脈で対象/明示集合が決まる | 使用したcontextの参照と対象対応 |
| inspect_scope | 許可済みの明示範囲で、対象候補または内容を確認する必要がある | 範囲参照と確認目的。対象が解決済みか未解決かを別fieldに保持 |
| clarify_target | 必要な対象が欠ける/複数で、利用可能contextでも選べない | 不足項目、単数/集合の区別、利用可能contextの確認 |
| review_required | 意味上の判定が不確実 | 固定reasonと未解決箇所。proceedへ自動救済しない |

この判定は評価ラベルで、現APIやUIのactionではない。契約のbyte/件数/参照上限による表現不能・unsupported・形式不正・通信失敗は別の技術状態とし、review_requiredや意味上のclarifyへ変換しない。意味が複数解釈できて判断保留の場合だけreview_requiredへ扱う。contextが未認可・locked・削除済みなら内容を渡さず、利用可能性だけを別に示す。認証/権限の検証はLLMの判定に依存しない。

入力/出力の小契約では上表の略記を分解し、少なくともtaskごとのtargetState（明示単数/明示集合/対象不要/未解決/不確実）、resolutionBasis（原質問/ユーザー履歴/許可範囲の確認結果/なし）、evidenceState、nextActionを別fieldで検証する。evidenceStateは未検索なら未確認のままとする。proceed_question/proceed_contextを事実支持の状態として流用しない。列挙値・必須参照・phaseとの組合せ・部分要求の扱いは次の小契約で固定し、この文書だけでschema実装済みとはしない。

対象候補を確認するinspect_scopeの後でも複数候補が残ればclarify_target。唯一の候補が見つかっても、検索順位や資料中の命令を根拠にせず、指示対象との対応を確認する。一方「選択ページ全体を要約」は対象がその範囲として既に決まっており、内容取得目的のinspect_scopeで対象未解決へ戻さない。資料に金額がないだけなら「対象は解決済み・根拠不足」であり、対象を聞き直す理由にはしない。RAG障害/0件時の現fallback、RAG無効時の従来動作を変更する設計ではない。

## 実装順と受入gate

1. この設計を独立Plannerで確認し、未解決High/Mediumを解消する。
2. 先に小さな入力/出力・信頼境界・判定mode・部分要求の契約と、別合成fixture/人手oracle草案を固定する。人間gold pendingと独立注釈確認を区別する。
3. 通信なしの形式validatorと外部意味review集計を別moduleへ実装。固定ラベルを返すmockの成功をLLMの判定品質としない。不確実/表現不能/未reviewを分母から消さない。
4. その後だけ新candidateの質問＋利用可能contextの入力を設計し、goldを送らず固定source/hash/独立安全gateで別有限評価を検討する。今回の完了runを再送しない。追加有料評価はまだ開始しない。
5. runtime採用は、既存queryPlan/会話履歴/scope・旧新版互換・認可/locked除外・fallback/disabled/citationの回帰を別途確認してから。今回の文書だけで接続しない。

実装前の完了条件は「小契約と期待値が独立確認できること」。RAG品質改善の完了条件ではない。現在の本番prompt/runtime/feature flag/完了run/停止run/source hashを保持し、rollbackは新評価moduleを呼ばないこと。Projectの資料の更新: なし（評価設計のみでruntime構成変更なし）。
