# ADR-0005 パスワード再設定の範囲、AIの上限の単位、フレンド一覧の鮮度

2026-10-09の独立レビューで出た4つの判断を、2026-10-10に決めた記録。

## 決定

1. **パスワードの再設定で、Passkeyも失効させる。** Passkeyはそのメールアドレスの所有の証明として扱われるため(`mintPasskeySession`)、古いパスワードを持つ者が先に登録したPasskeyが、再設定の後も使えてしまう。再設定は「アカウントを取り戻す操作」なので、そのアカウントのすべてのメールアドレスのPasskeyを消す(`revokePasskeysForEmails`)。本人はメールで本人確認ができ、サインイン後に登録し直せる。失効が完了しない場合は、新しいパスワードを保存せずに503を返す(古いパスワードのまま。再試行できる)。最初のパスワード設定では失効しない。
2. **再設定で、すべての端末をサインアウトする仕様は、そのまま維持して明記する。** サインアウトはサインイン方式ではなく、アカウント単位で切る。パスワードでサインインした端末だけを切る案は、乗っ取り犯が別の方式で入っているとそれが残り、実装も複雑になるので採らない。説明は `SECURITY_AND_PRIVACY.md` に書いた。
3. **フレンド一覧は、サーバーに最新を聞く。** `GET /api/chat/friends` は、KVを直接読むのをやめ、ユーザーのDurable Object(`UserRegistry.getUser`)を通して読む。KVの読み取りは別の拠点では最大約1分古くなりうるが、削除などの書き込みはこのオブジェクトの場所で行われ、そこでの読み取りには直ちに反映される。代償は、一覧を取るたびにDurable Objectを1回呼ぶこと(通信とリクエスト数が増える)。アプリ側の「削除から5分間は目印で隠す」処理はそのまま残す。
4. **AIの1日の上限は、アカウント単位で数える。** 以前は、サインインのたびに変わるトークンのハッシュを単位にしていたため、サインインし直す・別の端末で入る・退会して作り直すと、上限がリセットされた。アカウント(`ai-quota-account:<sub>`のハッシュ)を単位にする。複数の端末は、1日の枠を共有する。サービス全体の上限は、従来どおり。セッションが無い呼び出しは、従来どおりトークンのハッシュを使う。

## 影響

- 上限のカウンタは名前が変わるので、デプロイした日は、全員の上限が一度リセットされたように見える。
- フレンド一覧のDurable Object呼び出しが増える。フレンド一覧のポーリング間隔と、KV節約の方針(別カード)を見直すときの材料にする。
- 再設定時のPasskey失効は、KVの `passkeys:credential:` と `passkeys:user:` を走査する(メールアドレスで絞る)。Passkeyが多数になったら、メールアドレスごとの索引にする。

## 採らなかった案

- Passkeyを残して、画面で見直しを促す: 本人が見落とすと、乗っ取り犯が残る。
- パスワードでサインインした端末だけを切る: 上の2を参照。
- 上限を今のまま(トークン単位): リセットが簡単にできる。
