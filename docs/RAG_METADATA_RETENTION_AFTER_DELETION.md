# 退会後に残るRAG(PDF取り込み)の記録と、プライバシーポリシーの文面案

2026-11-06。**文面の案であり、公開してよい文面ではない。** プライバシーポリシーの変更は公開内容の変更で、法務確認(GitHub Projectの「法務確認」項目)の対象。ここでは事実の整理と案までを行い、ポリシー本体・配備済みの文書は変更していない。

## 何が残るか(コードとスキーマから確認した事実)

退会の処理(`account-deletion.ts`)は、アカウントのテキスト・ベクトルの削除を確認するが、**PDFの取り込みの記録(`rag_pdf_jobs`と、その元になるintake)は消さない**。消すための物理削除(purge)は、スキーマ上`physical_purge_enabled`が`0`に固定されており(`0028_rag_pdf_retention.sql`、`CHECK(physical_purge_enabled=0)`)、**現状は有効にできない**。このため、記録は退会後も残る。

| 残るもの | 内容 | 残さないもの |
|---|---|---|
| `rag_pdf_jobs`(1取り込みにつき1行) | 取り込み枠の会計用の記録: アカウントの識別子(ハッシュ。照合可能なので匿名ではない)、資料ID、取り込みの識別子、世代、同意の版、状態、日窓、予約/精算した単位数、期限、作成/精算の時刻、処理用の識別子のハッシュ | PDFの本文、資料の題名、PDFの元のダイジェスト、解析結果(`0026`の注記) |
| intakeの最小行 | アカウント/資料/最新の世代/取り込みの識別子/同意の版/期限(旧い要求の復活を拒否するための記録) | PDFのダイジェストと長さは、期限切れや取消の後にNULLにする設計 |
| 処理の復旧用の記録(recovery) | 親のjobが未精算の間だけ保持し、精算後に親と同時に削除する設計 | |

残す目的(設計文書 `RAG_PDF_RETENTION_DESIGN.md`):
1. **1日あたりの取り込み回数の制限の会計。** 当日の記録を消すと制限を迂回できる。
2. **退会・同意撤回・削除済みの資料の「復活」を防ぐ。** 古い要求が遅れて届いたときに、削除済みの資料や古い世代を新規として処理しないための拒否用の記録。
3. 処理が止まったかどうかが分からない取り込みの追跡。

## 保持期間の現状

- 設計上の通常の整理: 精算済みjobの詳細は、精算から**48時間以上**、かつその日の窓が閉じ、取り込みが取消/置換済みになってから候補になる。ただし、これは暫定の運用案で、延長する場合は版を分ける。
- **実装の現状: 物理削除は有効にできないため、期間の経過では消えない**(退会後も残り続ける)。intakeの最小行は、設計上も「当面は行全体を削除しない」。
- 本番のD1の実際の行数・内容は、**確認していない**(読み取りも行っていない)。

## ポリシーの文面案(法務確認が要る)

> **PDFを取り込む機能(資料の自動索引)の記録について**
> 資料の検索・要約のためにPDFを処理する際、1日の取り込み回数の管理と、削除済みの資料や古い要求が再び処理されることの防止のため、次の記録をサーバーに保存します。アカウントの識別子(暗号化された値)、資料と取り込みの識別子、同意の版、処理の状態と回数、時刻。PDFの本文、資料の題名、解析結果は含みません。
> アカウントを削除した後も、この記録は残ります。記録から個人を直接特定できる情報(氏名・メールアドレス・本文)は含まれませんが、アカウントの識別子と結びつけて照合できます。保持期間は、削除の仕組みの整備が完了するまで定まっておらず、整備後は[ __ ]日以内に削除します。

## 判断が要ること(責任者・専門家)

1. 上の文面で足りるか。特に「個人を直接特定できる情報を含まない」と書いてよいか(アカウントの識別子のハッシュは照合可能で、匿名化ではない)。
2. 「削除の仕組みが整うまで定まらない」と書いて公開してよいか。それとも、**物理削除を先に実装して期限を書く**か(High領域: 削除・保持に関わるので、独立レビューが必要。設計は`RAG_PDF_RETENTION_DESIGN.md`にある)。
