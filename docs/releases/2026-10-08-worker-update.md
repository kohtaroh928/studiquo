| 指摘 | 修正 | 確認 |
| --- | --- | --- |
| H1(再登録後の再退会で何も消えない) | 再サインイン(`mintSession`)で、退会完了の印(`deleted`)を、`{status:"active", reregisteredAt}` に置き換える。`deleteAccount` は、この印があるとき、再登録より前のジョブ(または無いジョブ)を、古い退会の再実行として何もせずに終える。再登録の後の本人の要求は、通常どおり全削除する | ローカルの実サーバーで再現→修正後に通過。テストあり(修正前のコードでは失敗) |
| H2(退会後に再登録できない) | RevenueCat削除ジョブは、サインインした同じ識別子のものを破棄して、サインインを通す(別名のジョブは残す)。退会の再試行は、`PRIVACY_RETENTION_ENABLED` が `false` でも、定期ジョブで処理する(1種類あたり2件まで)。`REVENUECAT_SECRET_API_KEY` が無いときは、RevenueCatのジョブの処理を省略し、溜まっていれば警告を1行出す | 同上 |
| H3(再登録・再購読してもプランが無料のまま) | 戻った時点で、そのアカウントの全識別子の `privacy_deleted_customers` の行を、1回のDELETEで消す。退会完了時に、別名にも印を書く(別名が先、正規が最後)。消せなかったときも、新しい口座は始め、消せなかった分を覚えて次のサインインで再試行する | ユニットテスト(実際のSQLiteとWebhook)。ローカルの実サーバーでは、サインインと退会の経路まで(Webhookは未確認) |

## 10. 公開実行・停止・復旧(案)

実行順(案。各操作は個別に明示的な承認が必要):
1. 対象commitを決め、クリーンなチェックアウトで `npm test` と `wrangler deploy --dry-run` を実行する。
2. ステージング(`--env staging`)にmigration 0005とWorkerを適用して確認する。
3. 本番D1にmigration 0005を適用する。0005は追加型で、`PRIVACY_RETENTION_ENABLED` が `"false"` の間は処理が動かない。
4. 本番Workerをデプロイする(`ARGON2_WRITE="false"`、`PRIVACY_RETENTION_ENABLED="false"`)。
5. 監視期間(期間は未定)を置き、問題がなければ `ARGON2_WRITE="true"` で2回目をデプロイする。
6. 新アプリを配布する。

復旧(案):

- migration 0005: 追加型。戻す場合は、機能を無効のままにして、別途判断する。
- データ復元: 別の承認と、削除要求との照合が必要。コードを戻しても、削除済みデータは戻らない。
