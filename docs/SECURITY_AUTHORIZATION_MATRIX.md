# API認可マトリクスの検証

実施日: 2026-11-04。基点: `origin/main` の `31599e6`。作業ブランチ: `codex/authz-matrix`。

## 結果と範囲

追加した675テストは全成功（失敗・skip 0）。133個のHTTPメソッド×経路を台帳化し、認証必須94、Access必須22、各フローで証明を要求する公開経路17に分類した。台帳の正本は `security/authz/routes.ts`。

既存サーバーテスト全体（`node --test --test-timeout=60000 --test-reporter=dot "src/*.test.ts"`）も終了コード0。Worker本体・既存テストの型検査と、DAST/認可テストの型検査も成功。別エージェントによる独立コードレビューで、分類漏れ、challenge不足、除名後のグループ操作、後片付け、readiness正例不足を指摘され、すべて対応後に追加の修正指摘なしとなった。独立レビュー担当によるテスト再実行はしていない。

本番のHTTPハンドラーをbundleし、一時Miniflare/workerd上の実D1・SQLite Durable Objects・KVで実行。全SQL migrationを適用した。利用者・資料・鍵は実行時の合成データのみで、実ユーザーや学習資料、クラウドの資格情報は使用しない。外部fetchは拒否して試行件数も0であることを検証。cronは起動しない。

本番の認可処理は変更していない。検証用wrapperが差し替えるのはローカルAccess公開鍵セットとレート制限（認可に到達するため常に成功）のみ。セッションは検査用KVに発行済みレコードを用意し、通常の `realSession` / 失効検証を通す。署名トークン必須とApp Attestはこのruntimeでは有効化していないため、その実装の検証は既存の専用テストに依存する。

| 境界 | 今回の検証 |
|---|---|
| セッション必須94経路 | 未認証・未発行・期限切れ・失効したtokenの拒否。パスキー登録verifyはtokenに紐づくchallengeを準備し、期限・セッション・失効のチェックまで到達させる |
| Access必須22経路 | 上記に加え一般利用者の拒否、別audienceの署名済みJWTの拒否、管理書込の正規Access付きcross-site拒否。7種の管理読取と報告画像には正規Accessの許可対照あり |
| 共同編集 | owner/editor/reviewer/非メンバー/除名済み。状態・参加者一覧、提案、承認、招待、除名、退出。拒否後に内容・参加者が変わらないことも確認 |
| チャット | 1対1とグループのメッセージ閲覧・送信・照合・編集・取消・通報、既知IDの添付取得・アップロード、既読。グループでは除名済みの利用者も拒否 |
| グループ管理・招待 | 作成者/一般メンバー/非メンバー/除名済みで名前・写真・招待・除名を検証。グループにはowner権限の区別がなく現メンバーは対等。招待は宛先本人だけが承諾/辞退でき、再使用不可 |
| アカウント内の資料・連携 | actionsの閲覧/削除、MCP inboxの列挙/確認、MCP grantの列挙/失効、libraryIDで他アカウントのIDを指定してもそのアカウントに作用しない |
| パスキー・画像 | 他人のメールで登録できないこと、正規所有者のoptions発行、他人のchallengeを消費できないこと、報告画像は報告者にもAccessを要求、avatarは本人/フレンドに限定 |
| RAG | 他人のdocument/source IDで状態・status・readinessが露出しない、state変更と2形式のsource削除が他人に作用しない、所有者の操作は成功 |
| 経路台帳 | 子ディレクトリを含むリテラル/正規表現の経路・明示methodガードと照合。GETを残してPOSTだけ外す変異、RAG子経路を外す変異で台帳検査が失敗することを確認 |

初回に既存の台帳がpublicとしていた報告・診断・利用イベントPOSTと報告画像GETを、現行コードに合わせて認証必須/Access必須へ分類した。メッセージPOST、端末登録/解除、グループ写真GET、招待辞退、RAG子経路、管理更新系なども台帳へ含めた。これは既存の検証範囲の補完であり、実装の認可脆弱性を発見したという意味ではない。

## 再実行

```sh
cd mcp-server
npm ci --ignore-scripts
npm run security:authz
node_modules/.bin/tsc -p ../security/tsconfig.json
```

通常CIのWorker testsジョブにも型検査と本マトリクスを追加した。外部接続、Docker、iPad、ログイン情報は不要。Miniflareのローカルポートとworkerd子プロセスの起動が可能な環境が必要。

## 判定の限界

- 「全APIで全ユースケースの安全を証明した」という結果ではない。公開認証/OAuth/Webhookの正常フローや暗号検証は専用の既存テストが担当する。台帳に載せただけの公開経路を、今回の認可マトリクスで正常フロー完走済みとは数えない。
- 94経路すべてに所有者/メンバーの区分があるわけではない。共有リソースには役割別の許可/拒否、本人専用APIにはアカウント分離、管理APIにはAccessという別々の基準を適用した。全保護経路の拒否を網羅することと、全業務フローの正常操作を網羅することは区別する。
- 経路のソース照合は現行の記述規則に限定する。動的RegExpやprefixで生成される全組合せを任意のTypeScriptから証明する解析器ではない。新しいルーティング形式では台帳と検出処理の見直しが必要。
- 実CloudflareのKV伝播・同時実行、edgeのAccess設定、TLS、実OAuthプロバイダー、実AI、実課金、PDF処理サービスやiPadは検証していない。runtimeのcompatibility dateは安定Miniflareに合わせた2026-07-30。
- 本番・ステージングへの配備、push、mergeは実施していない。テストのみのため、停止はCIの追加ステップを外すこと、ロールバックは本ブランチのテスト関連差分を戻すことで可能。
