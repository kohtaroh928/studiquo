# 監視とアラート

何が起きたら誰がどう知るか、知ったら何をするか。手順は[RUNBOOK](RUNBOOK.md)、設定は`mcp-server/src/ops-alerts.ts`と`login-monitor.ts`。

## 前提(これが無いとコードのアラートは出ない)

- Workerの `SLACK_ISSUE_REPORT_WEBHOOK_URL` が設定されていること。**未設定だとすべてのSlackアラートが黙って出ない**。配備のたびに設定の有無を確認する([RELEASE_CHECKLIST](RELEASE_CHECKLIST.md))。
- アラートは1種類につき**1時間に1回まで**。件数が増え続けても連投しない。本文に利用者のメール・ID・トークンは入れない。
- 閾値は、実際の利用の規模が分かるまで保守的(少ない件数で鳴る)に置いてある。規模が分かったら見直す。

## 稼働の監視(Workerの外から見る)

- `GET https://api.studiquo.app/health` が `200` であること。応答に `cronAgeSeconds`(毎時のcronが最後に動いてからの秒数)が出る。
- **外部の死活監視(UptimeRobot、Better Stack、Cloudflare Health Checksなど)で次を設定する(未設定)**:
  - `/health` が200でない、または応答が遅い → 通知。
  - `cronAgeSeconds` が **7200(2時間)** を超える → cronが止まっている。削除ジョブと保持期間処理が止まっているので、RB-08。
  - 通知先は連絡先表([RUNBOOK RB-19](RUNBOOK.md#rb-19-通知義務の確認項目責任者が専門家に確認する))の技術担当。
- cronが止まったことは、cron自身ではアラートできない(止まっているため)。外部監視が必須。

## まだ自動では知れないもの(正直な一覧)

- メール送信・プッシュ送信の**急増**: アドレスごと・IPごとの上限はあるが、全体の急増を知らせるアラートは未実装。Resendの通知で代替する(上の表)。
- AI料金: コードの全体上限(`GLOBAL_*_DAILY_LIMIT`)はあるが、金額のアラートは各社のダッシュボードの設定による。
- 漏えいパスワードの照合を飛ばしたこと(`pwned-passwords check skipped`): ログのみ。
- KV・D1・DOの上限への接近: Cloudflare側の通知に頼る。

## 見直しの時期

- リリース直後の1週間は毎日、その後は週1回、Slackとログのアラートの件数を見て閾値を調整する。
- 実際にアラートが鳴ったら、[対応記録](incidents/README.md)に残し、閾値が適切だったかを書く。
