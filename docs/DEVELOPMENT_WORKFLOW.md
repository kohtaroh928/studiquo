# Studiquo Development Workflow

このファイルは、Studiquoを開発する人間とAIエージェントの詳細な開発手順である。
`AGENTS.md`で`開発手順: full`が選択された場合、またはHighリスク変更を扱う場合に読み、
ユーザーの明示的な指示と矛盾しない範囲で従う。

## 1. プロジェクトの前提

- `studiquo/`: iPad向けSwiftUIアプリ。SwiftData、認証、課金、手書き、PDF、AI連携を含む。
- `studiquoTests/`と`studiquoUITests/`: iOSのユニットテストとUIテスト。
- `mcp-server/`: Cloudflare Workers上のAPI・MCP・認証・AIプロキシ。
- `project.yml`: XcodeGenの正本。生成済みXcodeプロジェクトだけを正本にしない。
- アプリとサーバーは独立して更新される可能性がある。API変更は前方・後方互換性を検討する。

## 2. 常に守る原則

1. 推測より証拠を優先する。変更前に関連コード、テスト、設定、履歴を確認する。
2. 症状だけでなく原因を修正する。場当たり的な回避策を恒久対応にしない。
3. 要求された範囲を守る。無関係なリファクタ、改名、一括整形を混ぜない。
4. 既存の未コミット変更はユーザーの作業として扱い、上書き・破棄・巻き戻しをしない。
5. 既存の設計、命名、UI、エラー処理、テスト方式に合わせる。逸脱には理由を残す。
6. APIキー、トークン、個人情報、学習内容をコード、ログ、テストデータ、コミットへ入れない。
7. 完了を主張する前に、変更内容に比例した検証を実行し、結果を確認する。
8. push、merge、release、deploy、ストア提出、本番データ変更は、ユーザーの明示的な依頼なしに行わない。

## 3. 変更のリスク分類

作業開始時に、変更を次のいずれかへ分類する。迷う場合は一段高い分類を使う。

### Low

- 文言、コメント、ドキュメント、局所的で挙動を変えない整理。短い調査と限定的な検証でよい。

### Standard

- 通常の機能追加、不具合修正、UI変更、API追加、永続化に影響しないリファクタ。受け入れ条件、実装計画、関連テスト、差分レビューを必要とする。

### High

- 認証・認可、課金、秘密情報、個人情報、アカウント削除、データ移行・削除、互換性破壊。
- 外部公開API、セキュリティ境界、AI利用量制御、本番設定、デプロイ。
- High変更では、実装前の設計、脅威・障害分析、ロールバック方法、独立レビューを必須とする。
- 取り返しのつかない操作または外部影響が生じる前に、ユーザーへ判断を求める。

Low変更には過剰な文書や会議相当の手順を課さない。

## 4. 標準開発フロー

### Phase 0: 依頼を理解する

- 解決すべきユーザー価値または不具合を一文で表す。
- 変更対象、変更しない範囲、制約、完了条件を明らかにする。
- 曖昧さが結果を大きく変えない場合は、仮定を明記して進める。
- 曖昧さがデータ、安全性、課金、公開仕様を変える場合は、実装前に確認する。

### Phase 1: 現状を調査する

- `git status` と現在のブランチを確認する。
- 関連する実装、呼び出し元、データモデル、設定、テスト、ドキュメントを検索する。
- 既存の振る舞いをテストまたは再現手順で確認する。不具合修正では可能なら先に再現する。
- 外部SDKやサービスの仕様に依存する場合は、公式の最新資料を確認する。
- 調査で見つけた既存の未コミット変更と、自分が行う変更を区別する。

### Phase 2: 要件と受け入れ条件を決める

Standard以上では、実装前に少なくとも次を定義する。

- 正常系で利用者が何をでき、空状態、通信失敗、キャンセル、再試行、権限不足でどう振る舞うか。
- アクセシビリティ、ローカライズ、iPadの画面サイズや向きへの影響。
- アプリ旧版とサーバー新版、またはその逆の組み合わせで壊れないか。
- テスト可能な受け入れ条件。

### Phase 3: 設計する

- 既存構造へ最小の責務追加で収める。新しい抽象化は複数箇所で価値がある場合に導入する。
- UI、ドメインロジック、永続化、ネットワーク、外部サービスの責務を分離する。
- API変更では、入力検証、認証・認可、冪等性、タイムアウト、再試行、レート制限を検討する。
- データ変更では、移行、既存データ、途中失敗、再実行、ロールバックを設計する。
- High変更では、悪用ケース、障害モード、監視方法、段階的公開、停止方法を記録する。
- 大きな機能や設計変更は、実装前にPlannerで影響範囲とトレードオフを独立して整理する。

### Phase 4: 実装計画を作る

- 変更をレビュー可能な小さい単位へ分ける。
- 依存関係の順に、対象ファイル、変更内容、検証方法を並べる。
- 必要なテストを実装と同じ計画に含める。
- スコープ外の改善点は勝手に実装せず、別候補として記録する。

### Phase 5: 実装する

- まず最小の縦切りで動作を通し、その後にエラー処理と境界条件を固める。
- 公開インターフェースとデータ形式は、明確な移行計画なしに破壊しない。
- エラーは利用者に行動可能な形で伝え、内部ログには診断可能な文脈を残す。
- ログへ秘密情報、認証情報、ノート本文などの機微情報を出さない。
- 一時的な回避策、feature flag、互換コードには削除条件を残す。
- 生成物ではなく正本を編集する。`project.yml`変更時はXcodeGen再生成後の差分を確認する。

### Phase 6: 検証する

変更に最も近いテストから始め、影響範囲に応じて広げる。

#### iOS

- ロジック変更には原則として`studiquoTests/`のユニットテストを追加または更新する。
- 主要導線、画面遷移、回帰リスクが高いUIには`studiquoUITests/`を検討する。
- 対象テスト、関連テスト、ビルドの順で確認する。実機差がある機能はシミュレータだけで完了としない。
- `project.yml`変更後は`xcodegen generate`を実行し、署名・entitlements・Capabilitiesが保持されたか確認する。
- XcodeGenにはネストした`SystemCapabilities`の既知の制約があるため、Apple Sign InとCloudKitを特に確認する。

#### Cloudflare Workers

- `mcp-server/`の変更では、まず対象テスト、次に`npm test`を実行する。
- 認証、認可、入力検証、テナント分離、エラー時の情報漏えいをテストする。
- D1 migrationは追加型かつ再現可能にし、既存環境へ適用済みのmigrationを書き換えない。
- 外部AI、RevenueCat、APNs、OAuthは成功だけでなく、タイムアウト、上限、無効資格情報、再試行も確認する。
- 本番デプロイは検証ではない。ローカル・テスト環境で確認してから、別工程として扱う。

#### テスト品質

- 不具合修正では、可能なら修正前に失敗し修正後に成功する回帰テストを追加する。
- 実装詳細ではなく利用者から見える契約をテストする。
- 時刻、乱数、ネットワーク、外部サービスは決定的にテストできる境界を設ける。
- テストを削除・弱体化して通すことを解決策にしない。
- 実行できない検証は、理由と残るリスクを明示する。

### Phase 7: レビューする

実装後はコードを変更した視点と別の視点で確認する。

- 要件と受け入れ条件をすべて満たしているか。
- 認証・認可、入力値、並行処理、状態遷移、データ境界に抜けがないか。
- 後方互換性、migration、障害時の復旧が成立するか。
- テストが正常系だけに偏っていないか。
- 無関係な変更、デバッグ出力、秘密情報、不要な依存が入っていないか。
- Standard以上ではCode Reviewer、セキュリティ関連ではSecurity Reviewerによる独立レビューを優先する。
- 指摘は重大度、再現条件、影響、修正案を具体的に示す。

### Phase 8: 引き渡す

完了報告には次を含める。

- 何を、なぜ変更したかと、変更した主要ファイル。
- 実行したテスト・ビルドと結果、実行できなかった確認と残存リスク。
- migration、設定変更、リリース順、ロールバックなど運用上の注意。
- ユーザーが次に判断または実行すべきことがある場合のみ、その手順。

## 5. Gitと変更管理

- `main`または`master`へ直接実装・コミットしない。
- 作業前にブランチとworking treeを確認する。適切な作業ブランチ上なら継続してよい。
- 未コミット変更がある状態で、勝手にブランチを切り替えたり新規作成したりしない。
- 新規ブランチは目的が分かる短い名前にする。Codexでは原則`codex/`接頭辞を使う。
- 1つの変更セットには1つの目的を持たせる。機械的整形と機能変更を混ぜない。
- コミット前に`git diff`と`git status`を確認し、自分の変更だけを含める。
- force push、履歴改変、破壊的reset、ユーザー変更の破棄を行わない。
- コミット、push、PR作成は依頼された範囲でのみ行う。

## 6. セキュリティ・プライバシー・データ

- クライアント入力とAI出力は信頼しない。型、長さ、形式、権限をサーバー側で検証する。
- 認証と認可を分けて確認する。ログイン済みでも、対象データへの権限があるとは限らない。
- アカウント・端末・テナントをまたぐIDOR、権限昇格、データ混線を防ぐ。
- トークンは必要最小権限、期限、失効、ローテーションを考慮する。
- 秘密情報はWrangler secretsや適切な秘密管理に置き、アプリやリポジトリへ埋め込まない。
- 収集・保存・送信する個人情報を最小化し、削除要求と保持期間を考慮する。
- アカウント削除は関連データ、外部連携、再試行、部分失敗を含めて設計する。
- 依存追加は必要性、保守状況、ライセンス、脆弱性、バイナリサイズを確認する。

## 7. リリースと運用

- リリース前に、対象バージョン、設定差分、migration、互換性、監視、ロールバックを確認する。
- アプリとサーバーの順序依存がある場合は、旧版との互換期間を設け、順序を文書化する。
- migrationはバックアップまたは復旧方法を用意し、小さく段階的に適用する。
- 段階公開やfeature flagが使える場合は、高リスク変更を一度に全ユーザーへ出さない。
- リリース後に主要導線、エラー率、認証失敗、利用量、外部サービス失敗を確認する。
- 障害時は、影響抑制、事実の記録、復旧、原因分析、再発防止の順で進める。

## 8. Definition of Done

次を満たすまで完了としない。

- 要求と受け入れ条件を満たしている。
- 正常系、主要な異常系、回帰を検証している。
- 関連テストとビルドが成功している、または未実施理由が明示されている。
- セキュリティ、プライバシー、互換性、migrationへの影響を確認している。
- 必要なドキュメントと設定例を更新している。
- 差分に無関係な変更、デバッグコード、秘密情報がない。
- リリース方法とロールバック方法が必要な変更では、それらが明確になっている。
- 人間がレビューできる要約と検証結果が揃っている。

## 9. エージェントの使い分け

利用可能な場合は、責務を混ぜず次の役割を使う。

- Explorerは事前調査、PlannerはStandard以上の設計と計画を担当し、どちらも実装しない。
- Implementerは合意済みスコープを実装し、Test Writerは不足するテストを追加・実行する。
- Code Reviewerは別視点で差分を確認し、Security Reviewerは認証・入力・秘密情報・個人情報を確認する。
- Documentationは文書を更新し、Release Managerは証拠を集約してGo/No-Go判断材料を提示する。

小変更では不要な役割を増やさない。High変更ではPlanner、Code Reviewer、必要に応じてSecurity ReviewerとRelease Managerを使い、実装者だけの判断で本番へ進めない。
