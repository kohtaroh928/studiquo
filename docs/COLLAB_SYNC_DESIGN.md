# 共同編集: 文書全体の自動同期(設計)

状態: 実装済み(2026-11-09、ブランチ `claude/collab-invite-screen`)。ステージング未配備・実機未確認。

## 目的

共同編集の変更を、承認なしで、文書の全内容(段落の追加・削除・並べ替え、表、画像、文字の書式、コメント、脚注、ヘッダー・フッター、題名・用紙・段組み)について、参加者の端末へ自動で反映する。これまでの「提案→承認」は、段落の文字だけが対象で、承認しても本文に入らなかった。

## 方式

- 文書全体を1つの**スナップショット**(JSON)にして、ルーム(Durable Object)に**版番号つき**で保存する。サーバーは中身を解釈しない。
- 書き込みは「基準の版」を添える。基準が現在の版と違えば409(競合)。書く側は、最新を取って**3者マージ**(共通の祖先=前回同期した版、自分の版、相手の版)してから、もう一度書く。
- マージは**ブロック単位**(各ブロックに端末をまたぐ固定ID `collabID`)。片方だけが触ったブロックはその版、両方が触ったブロックは**この端末(後に保存する側)の版**を残し、競合として画面に出す。片方の削除と他方の編集が重なったら、編集を残す。順序は、並べ替えた側に従う。題名などの単独項目は項目ごとにマージ。
- **画像**はスナップショットに入れず、中身のSHA-256を名前にして別に保存する(サーバーが名前と中身の一致を検証)。1枚あたり約4.4MBまで。超えた画像はその端末にだけ残る。
- アプリは、文書を開いている間、**約4秒ごと**に同期する(送信・受信)。閉じるときにもう1回。入力中にネットワーク呼び出しが挟まって本文が変わった回は、反映せず次に回す(入力を上書きしない)。
- 権限: 作成者と編集者は読み書き、レビュアーは読み取りのみ(書き込みは403。レビュアー側の編集は次の同期で元に戻る)。

## 限界(既知)

- 同じ段落を同時に編集すると、片方(後に保存する側)の内容が残る。
- 段落の途中を同時に編集しても、文字単位では統合しない。
- 4秒ごとの取得なので、反映は数秒遅れる。リアルタイムではない。
- 画像が1枚4.4MB超、スナップショットが6MB超、1ルームの画像合計が約45MB(base64で60MB)超だと、共有できない。
- 既存の共有(スナップショットなし)は、作成者の最初の同期で作られる。古いアプリの端末は、新しい内容を受け取れない。

## 独立レビューの指摘への対応(2026-11-09)

- 空の部屋の最初のスナップショットは作成者だけが書ける(サーバーで強制。編集者は412で待つ)。旧版で共有された文書を、招待された人が先に開いても、作成者の内容を簡易版で上書きしない。
- 同期の基準(版・基準のスナップショット)は、iCloudで同期されるSwiftDataのモデルではなく、**端末の中**(UserDefaultsとApplication Supportのファイル)に持つ。他の端末の基準が混ざって、他人の変更を取り消す内容が送られるのを防ぐ。
- 段落の同期IDは、内容が同じ段落を先に対応づけ(最長共通部分列)、残りだけを位置で対応づける。段落の挿入・削除で、後続の段落のIDがずれない。
- 入力中の判定は、書式を含む本文全体(`NSAttributedString`)と文書の内容を比べる。
- スナップショットが参照しなくなった画像は、書き込み時にサーバーが削除する(直近10分に上げた画像は残す)。
- 画像のアップロード・スナップショットの書き込みは、本文を読む前に権限を確認する。不正なbase64は400。
- 閉じるときの最後の同期は、進行中の同期を待ってから行う。レビュアーが消した画像は、元の画像を取得して戻す。
- 残る限界: 403をすべて「レビュアー」と表示する(退室させられた人も)。部屋が作り直されて版が偶然一致すると取り込まれない(極めてまれ)。同期ごとに全画像のハッシュを計算するため、大きな文書では重い。

## サーバー

- `GET/PUT /api/document/rooms/:id/snapshot`、`POST .../assets/missing`、`PUT/GET .../assets/:sha256`。
- 保存は2MB未満の断片に分割(Durable ObjectのSQLiteの1値の上限)。
- **削除**: ルームの消去(作成者のアカウント削除)・最後の参加者の退出で、スナップショットと画像も消える。参加者の削除では、スナップショットの最終更新者の記録を空にする。テストで確認。
- 互換: 追加のAPIだけ。古いアプリは従来どおり提案・承認の経路を使える(新しいアプリは使わない)。サーバーを先に配備してよい。
