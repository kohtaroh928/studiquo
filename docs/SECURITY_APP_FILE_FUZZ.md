# アプリのファイル・テキスト解析のファジング

2026-11-05、`origin/main`の`31599e6`を基点に、専用ブランチ`claude/app-file-fuzz`で実施した。サーバー(Worker)の入力ファジングは別ブランチ(`codex/worker-fuzz`、`docs/SECURITY_WORKER_FUZZ.md`)で、ここには含まない。

## 結果

壊れた入力・巨大な入力で、**アプリが異常終了する入力が2種類(数式の入れ子、引用・箇条書きの入れ子)と、極端に遅くなる処理が6種類**見つかった。すべてこのブランチで修正し、同じシードで再実行して解消を確認した。修正後の検査では所見が出ていない。ただし、これは有限のシード付き変異検査で、網羅的な検証ではない(下の「限界」)。

| 対象 | 見つかったこと | 修正 |
|---|---|---|
| 数式の解析(`MathExpressionParser`) | `{`を数千重ねるとスタックを使い切り、アプリが異常終了する | 入れ子60段で打ち切る |
| 引用・箇条書き(`RichTextParser`) | `>`を約1.5万重ねると、同じくスタックを使い切って異常終了する | 24段より深い記号は文字として扱う |
| 数式の整形(`MathTextFormatter`) | `\begin{align}`などを入れ子にすると、段ごとに本文を2回描画し、上限の60段では終わらない | 描画を必要な環境でだけ行う |
| テキストの分割(`MathSegmenter`) | 閉じないバッククォートの長い列で、毎文字ごとに列全体を数え直す(4.7万個で35秒)。`$`が多い段落でも、`$`ごとに段落の終わりまで走査していた | 閉じない列は全体を文字として扱う。走査を1回にまとめた |
| インラインの書式(`RichTextParser`) | 閉じない`[`・`*`が多い行で、開きごとに行末まで探索する(二乗) | 1テキストあたりの探索量に上限 |
| Markdown除去(`MathTextFormatter.plainText`) | 極端に長い1行で正規表現が後戻りし、数分かかる | 5,000文字を超える行は変換しない |
| docxの読み込み(`DocxReader`) | 約5KBのファイルが4.5万行の表に展開され、8〜11秒かかる(行数の二乗で増える)。本文パートの大きさに上限がない | 行の関連づけの重複を除き線形にした。本文パートは30MBまで |
| バックアップの復元(`NotebookBackupService`) | ページ数に上限がなく、ページ数の二乗で時間が増える(約4,000ページで9秒) | 上限5,000ページ。配列を集めて1回だけ代入し線形にした |

回帰テストは`studiquoTests/Fuzz/AppFileFuzzRegressionTests.swift`にある。時間の絶対値ではなく、入力を4倍にしたときの時間の伸びで判定する。

## 検査の内容

- 対象(入口): ZIP(`DocxZip`)、docx(`DocxReader`)、テキスト・マークアップ・数式(`RichTextParser`、`MathSegmenter`、`MathTextFormatter`の3関数、`MathExpressionParser`)、バックアップ(`NotebookBackupService.restore`)、画像(`ImportLimits.checkImage`+デコード)、PDF(`PDFImportService.extractPagesChecked`)。
- 入力: 実行時に合成した正しい入力(アプリ自身の書き出しを使用)を、シード付きの変異で壊す。ZIPの各ヘッダ項目、XMLの入れ子・巨大属性・外部実体、JSONの型・入れ子・要素数、画像の宣言サイズ、PDFの構文、テキストの記号列と入れ子など、形式ごとの変異と一般的な変異(ビット反転・切り詰め・複製・特殊値)。個人情報・実データは使わない。
- 判定: 異常終了、制限時間(対象ごと)、メモリ(`phys_footprint`を2msごとに採取)、不変条件(取り込み上限の遵守、外部実体を展開しない、復元結果の整合)。
- 再現: ケースは`(シード, 番号)`から作り直せる。各ケースの前に記録を書くので、異常終了したケースが分かり、次のケースから続行する。
- 検査器の自己確認: わざと壊したパーサー(異常終了・時間超過・過大なメモリ・不変条件違反)を同じ仕組みで流し、検出と再現が働くことを確認した。この確認で、検査器自身に範囲外アクセスがあることも見つけて直した(アプリの問題ではない)。
- 実行: `scripts/app-file-fuzz --target <zip|docx|text|backup|image|pdf> --seed N --cases N`(iPadシミュレータ、1回9分以内)。結果は`security-reports/app-fuzz/`(Git管理外)。終了コードは0=所見なし、1=所見あり、2=基盤の失敗(ケースが0件などは「問題なし」としない)。

実行したケース数(修正後のビルド、通常実行、所見0): テキスト・数式 24,000、docx 8,000、画像 36,000、ZIP 120,000、PDF 1,500。ASan+UBSan付き(修正後、メモリ上の誤りの報告0): テキスト 4,108、バックアップ 600、docx 1,000、画像 4,000、ZIP 20,000。ASan付きのテキスト検査で「遅い」と出た26件は、すべて73万バイト以上の入力(1バイトあたり2.6〜4.8マイクロ秒、サニタイザーの遅さの範囲で、比例して伸びる)で、二乗の兆候はなかった。上の所見は、修正前のビルドでの実行で出たもの。バックアップの復元は、最後の修正(線形化)の前に走らせた実行で5,000ページ付近の遅さが出たため、修正後は回帰テストで確認した(再度のファジングは未実施)。

## 限界

- シード付き変異検査で、coverage-guided fuzzingではない。形式ごとの変異は、見つかった所見の種類を左右する。深い構文木に届いた割合(カバレッジ)は、解析ファイルごとには測っていない。
- PDF・画像の実際のデコードはAppleのフレームワーク(PDFKit、ImageIO)で、その内部の欠陥はここでは見つけられない。入力の宣言サイズと上限(`ImportLimits`)の遵守は検査した。
- 時間の判定はDebugビルドのシミュレータで行った。Releaseの実機では短くなるが、入力サイズに対する伸び方(二乗か線形か)は同じなので、回帰テストは伸びで判定している。
- 共有拡張、サーバーから届くデータ(AIの応答・チャット)の解析のうち、上の入口を通らないものは含めていない。対象の入口の一覧は`studiquoTests/Fuzz/AppFileFuzzTests.swift`。
- 実機(iPad)では実行していない。
- アプリ全体のユニットテスト(2,080件)を修正後のブランチで実行し、51件が失敗した。失敗はKeychain・鍵・退会まわり(署名なしのシミュレータビルドで動かないもの)に集中しており、そのうち31件は、変更前の`origin/main`でも同じ31件が同じように失敗することを確認した。残る20件(認証のログアウト・パスキー・Keychain、保護ノートの暗号、MCP資格情報)は変更前で実行しておらず、変更箇所(解析器とバックアップ復元)とは別の領域である。
- 変更は独立した別のエージェントによるレビューを受けていない。mainへの統合の前に、レビューと、実機での取り込み確認(大きなPDF・画像・docx・バックアップ)が要る。

Projectの資料の更新: なし(テストと内部の修正のみ。取り込み上限の追加はあるが、利用者に見える仕様の変更ではない)。
