# 質問unit参照による要求分解：評価契約案

2026-10-15。今回は設計・オフライン反例の整理だけ。コード/API/キー読取は追加しない。

## 確認できた問題と未確定事項

前回v3の新runは4試行/3完了/1引用照合拒否、後続4未送信。成功3問の要求分割は独立監査で妥当。失敗payloadを保存していないのでtext/prefix/suffixのどこが不一致かは不明であり、引用方式そのものがモデルの誤りの根本原因だとは断定しない。旧runはlockを保持し再送しない。

本来測りたいのは、質問から回答すべき項目・対象・属性・操作・条件を落とさず整理できるかである。位置計数や厳密な複写の成功と、この意味評価を分離する候補を設計する。

## 候補と判断

| 候補 | 利点 | 制約・判断 |
| --- | --- | --- |
| A：v3厳密引用を維持 | 正確な原文対応、既存の比較基準を保持 | 引用と前後contextの複写が必要。既存結果/sourceを凍結保持する |
| B：正規化/fuzzyで失敗を救済 | 表記差を許せる可能性 | 別箇所や否定を含む表現の誤対応を成功扱いし得る。今回は不採用 |
| C：server生成unit ID参照 | offset計数と引用の複写をモデルから外せる | 粗い参照と自由ラベルの意味誤りを形式検証で検出できない。新評価契約として設計のみ進める |

Aの失敗出力をCへ変換して合格へ救済しない。CがAより高精度という証拠はまだない。本番prompt v1やretrieval/citation契約は変更しない。

## Cの入力：原文を保持するunit

- serverが質問の原文全体、SHA256のquestionHash、決定的なunit一覧を作る。モデルには原文とunit一覧を質問データとして渡し、全て命令でなく非信頼データとして扱う。gold/正解ラベル/評価ID/学習内容は渡さない。
- unitは質問中の文・行に対応する参照単位。句や文が意味上独立していると保証するものでも、RAG資料のchunkや出典でもない。
- 初期候補は文末記号・改行を境界にし、区切り文字・空白も含む原文をそのまま順番に保持する。日本語の文末、CRLF/連続改行、引用・括弧内記号、英数字の小数点や略語を含む境界ルールは、実装前に小さな契約として固定する。質問固有語による分岐は作らない。
- 全unitのtextを順番に連結すると元の質問に完全一致する。server管理のstart/endはUTF16で、孤立surrogateやsurrogate pair途中の分割を拒否。結合文字/ZWJのgrapheme境界は別に定義し、見た目やUnicode正規化で同一視しない。
- question最大16384 UTF8 byte、unit最大64を候補上限とする。切断・省略で収めず、表現できなければpreprocessing unsupportedとして明示する。質問自体の意味がunrecognizedだとは扱わず、評価から黙って除外しない。
- IDはu1..u64のような決定的な列。位置はserverだけが保持し、モデルに計算・出力させない。別質問の同じu1との混同を防ぐため、出力rootのquestionHashを入力原文のhashと必ず照合する。wire schemaでは期待するhashを単一enumにし、任意のhash値を受け付けない。

## Cの出力：要求候補と参照を分離

候補contract versionは4とし、既存v2/v3と分ける。v4を旧v2へ黙って変換したり、旧validatorを弱めて受理したりしない。rootにはversion/questionHash/status/tasks/unresolvedを持つ案とする。

- 各taskはid、operation、attribute、subjects、conditions、requestUnitIdsを持つ。attributeは `{label, unitIds}`、subjects/conditionsはその配列。task全体だけでなく各roleに参照を持たせる。
- labelはモデルが作った解釈候補。原文引用と名乗らず、retrievalの事実・根拠・回答へ格上げしない。対象や条件の勝手な補完は意味評価で誤りとして扱う。
- task最大16、subjects/conditions各最大4、label非空最大256 UTF16、各unitIds/requestUnitIdsは必須なら1..4・重複なし・既知IDのみを候補上限とする。省略された対象を補うためにラベルを捏造しない。対象/条件が明示されなければ配列は空を許す。
- 一つのunitに複数要求、一つの要求に複数unitを許す。unit数をtask数や必要な回答項目数とみなさない。同じunitを複数task/roleから参照してもよい。
- resolution/evidenceSupport/comparisonPermissionはunknownを維持し、質問の条件から資料支持・比較可否を決定しない。従来のoperation enumとstatus整合の規約を別契約へ明示して引き継ぐ。
- unresolvedはkindとunitIdsを持つ案。unresolved referenceとneeds_clarificationの整合、candidateにtask必須、unrecognizedはtaskなし+理由参照必須を保つ。unit上限やvalidator障害をsemantic clarificationへ自動変換しない。
- 各roleの参照上限4とunit上限64には表現能力の差がある。必要な条件が5unit以上に分散するなど、参照/byte上限で完全に表現できない場合は契約上の表現不能として扱い、切断・要求漏れ・意味不明・モデル失敗と混同しない。この必要参照数は正解を持たないvalidatorだけでは一般に判定できないため、評価oracleの表現可能性チェックと独立意味監査で別に報告する。候補上限は次の小契約で再確認し、未対応を成功率から隠さない。
- JSON plan最大32768byte、exact keys/型/件数/重複を検証する。位置は参照からserverが解決し、labelsを原文sliceへ偽装しない。

## 何を検証でき、何が残るか

localで検証可能：質問hash、IDの存在、空の必須参照、件数/文字長/byte、status整合、unknown固定値、unitと原文の復元・位置対応。

localだけでは検証不能：正しいIDが意味上その対象/属性/条件を支えるか、必要な参照が漏れたか、要求を過分割/結合したか、自由ラベルが原文にない対象を足したか。「省略IDを拒否」は必須欄の空を拒否する意味であり、全ての意味上の漏れを検出するものではない。

全roleに同じu1を付ければ形式が通る場合もある。一致IDや原文復元だけを正しい抽出と採点せず、この反例を評価に残す。質問内参照は資料の出典引用として返さない。unit本文/自由ラベルに命令が含まれても非信頼データのまま保持し、system指示やツール実行権限へ昇格させない。requestHash/questionHashも上流dispatchや意味支持の暗号学的証明ではない。

## 次の実装順とgate

1. unit境界の最小契約を固定し、pure preprocessorと上の反例をオフライン実装。通信・キー・本番接続を追加しない。
2. role別参照と質問bindingのschema/validatorを別moduleへ実装し、形式が通る意味誤りの負例を残す。
3. 既存開発oracleと意味上の要求数/role対応を一対一で比較できる評価規約を準備する。単なるID coverageや全文参照をrecallとして採点しない。手書き注釈の人間確認は引き続きpending。
4. その後だけ、質問のみrequest/response・固定予算・独立安全レビューを別単位で扱う。実モデル評価なしに採用しない。未使用20問は凍結のまま。

既存A/v3のsource/journal/結果は不変。追加API0、コード変更0、テスト再実行なし（今回は設計の証拠との照合のみ）。独立Plannerの比較・受入条件を反映した。Projectの資料の更新: なし。
